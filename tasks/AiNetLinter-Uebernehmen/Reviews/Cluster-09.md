**P2 — Health publishes an unavailable continuation instead of an actionable public recovery.** Location: `src/AiNetCodeNavigator/Mcp/Tools/Maintenance/MaintenanceTools.cs:84` (success builder composition).

- Reproduction: `tools/call get_server_health` with `maxResponseBytes=512,maxResponseTokens=40` returns `IsError=false`, `operation=ok, completeness=truncated`, only `Navigator host: running`, and `[Truncated; continue at UTF-16 offset 24; 277 UTF-8 bytes omitted.]`. The returned text is 137 bytes/37 tokens; the same initial complete snapshot is 344 bytes/104 tokens. Public `tools/list` exposes only `targetPath`, byte budget, and token budget. A follow-up with `startOffset=24` is rejected by the actual argument filter as `INVALID_ARGUMENT`, exactly `fieldPath: $.startOffset`; no continuation token is published. A repeated call at the same budget starts from the beginning of a fresh health snapshot.
- The 30–110 token sweep produced partial health success or sanitized `InvalidParams`, never a public `RESPONSE_BUDGET_TOO_SMALL`/minimum-token recovery. One-token rejection therefore does not establish useful public recovery for the larger health result. This finding concerns the new maintenance consumer's composition, not a renewed point 8.2/8.3 audit.
- Acceptance: make health an atomic snapshot with executable budget-recovery minima, or expose a supported stable continuation protocol. Do not publish an offset action absent from the tool schema. Cover a token budget that can fit a recovery envelope but cannot fit full health, retry with the exact advertised valid minima, and retain all health fields or an explicit complete recovery instruction. Only use protocol `InvalidParams` when the mandatory recovery envelope cannot physically fit.

**P2 — A response-budget rejection can publish configuration before returning InvalidParams.** Location: `src/AiNetCodeNavigator/Mcp/Tools/Maintenance/MaintenanceTools.cs:96` (reload before response construction at line 107).

- Reproduction: start with `Information`, version 1; write valid `Debug` settings and call `reload_config(maxResponseTokens=1)`. The caller receives JSON-RPC `-32602`, but the next normal health call reports version 2/Debug. A second nontrivial case writes valid `Warning` after version 4 and calls with `maxResponseTokens=22`; it also returns `-32602`, while health reports version 5/Warning. A complete normal reload acknowledgement in this runner needs 23 tokens. Settings publication precedes the builder's budget failure, so the rejected public invocation has already committed its effect and a caller's retry publishes another version.
- Acceptance: validate the public request and representability of the required acknowledgement before publishing candidate settings; a budget/protocol rejection must preserve version and effective log level. Coordinate candidate validation, response budgeting, and commit so concurrent reloads cannot invalidate the checked version/result. Test both one-token and near-acknowledgement budgets through the real host and verify the state after rejection.

**P2 — Reload's advertised idempotency contradicts its observable version contract.** Locations: `src/AiNetCodeNavigator/Mcp/Tools/Maintenance/MaintenanceTools.cs:90` and `src/AiNetCodeNavigator/Configuration/NavigatorHostConfiguration.cs:120`.

- Reproduction: the actual `tools/list` response advertises `reload_config.annotations.idempotentHint=true`. With an unchanged valid Debug file, two identical budget-default calls return versions 3 and 4 respectively; health confirms version 4. The configuration publishes a fresh version on every successful invocation, including an identical repeated request. The published settings version is therefore changed by repetition, not just the response text.
- Acceptance: align the annotation with the deliberate settings/version behavior. Either advertise a non-idempotent reload, or retain a stable published version for an unchanged candidate so repeating the same request has no additional observable settings effect. Verify tools/list and repeated calls together. Keep the separate budget-rejection preservation requirement above.
