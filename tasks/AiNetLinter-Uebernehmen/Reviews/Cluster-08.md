## Point 8.1: Budgeting and Truncation

- Implementation base: `c17efc44f1898cb905afd65f1b8dee66ac539a6c` (clean working tree); implementation commit is recorded after required gates.
- `McpResponseFormatter` is an internal host utility. It uses SharpToken `cl100k_base` for token counts and enforces inclusive public byte limits of 512 through 65,536, with a 16,384-byte default. SharpToken was moved from Core to the MCP host project.
- Responses preserve complete newline-delimited units. Truncated results carry a UTF-16 continuation offset and omitted UTF-8 byte count; callers can resume from that offset. A first unit that cannot fit returns `RESPONSE_BUDGET_TOO_SMALL` with the exact required byte and token counts. Invalid budgets, token caps, offsets, and malformed UTF-16 are rejected.

### Point 8.1 audit 1 findings

1. **P1 - An impossible retry budget is presented as recoverable.** `McpResponseFormatter.cs:79-84` computes the first-unit-plus-hint minimum without reconciling it with the public maximum of 65,536 bytes (`McpResponseBudgetLimits.cs:5-10`), then tells the caller to repeat with that value. Repro: source `new string('x', 65490) + "\n" + new string('y', 100)`, `maxResponseBytes: 65536`. The source is 65,591 UTF-8 bytes, while the required first unit plus marker is 65,562 bytes; the advertised retry is rejected by `Format` before it can return content. The same problem occurs for a single unit longer than 65,536 bytes. **Acceptance:** For every budget error, expose a retry path that is valid under the public contract, or explicitly report that this atomic unit cannot be returned within the supported range and offer a supported narrowing/pagination route. Add a boundary test at 65,536 bytes and above.
2. **P2 - A continuation offset inside a line silently returns a partial unit.** `McpResponseFormatter.cs:39-42,126-134` accepts every in-range UTF-16 offset except one inside a surrogate pair. For `"alpha\nbeta"` and `startOffset: 1`, the fitting success text is `"lpha\nbeta"`, contradicting complete newline-delimited units; the continuation test (`McpFormattingTests.cs:80-94`) only passes an offset produced by the formatter. **Acceptance:** Reject offsets that are not 0, end-of-text, or immediately after a newline, or define and test an explicit canonicalization rule that never loses source characters. Cover arbitrary valid UTF-16 mid-line offsets and valid generated offsets.
3. **P2 - Error responses can exceed a requested token cap.** `McpResponseFormatter.cs:73-95` returns a fixed multi-line `RESPONSE_BUDGET_TOO_SMALL` message without applying `maxResponseTokens`. For `Format("hello world from the navigator", 512, maxResponseTokens: 1)`, the multi-word source cannot fit one token and the returned error necessarily contains more than one token; `McpFormattingTests.cs:50-63` tests only a truncated success under a token cap. **Acceptance:** Specify whether token caps apply to errors. If they do, enforce the cap or reject unrepresentable limits before producing an over-budget response; test exact and below-minimum token boundaries. If errors are exempt by contract, document that exception and test it explicitly.

No public MCP stdio acceptance is claimed. The three findings are resolved by the implementation record below; the point audit checkbox remains open for independent follow-up.
