# Workspace architecture review evidence

Scope: current workspace loading, freshness, caching, framework coverage, and UI project evidence. These are observations of the checked-in implementation, not a task acceptance claim. No code was changed.

## Current behavior

- The server itself targets `net10.0` (`Directory.Build.props:3`) and setup requires the .NET 10 SDK/runtime for framework-dependent deployment (`docs/setup/README.md:3`). Source solutions are loaded through installed MSBuild/.NET SDK tooling with `MSBuildWorkspace`, not by targeting each application runtime from the server (`src/AiNetCodeNavigator.Core/Workspace/MSBuildSolutionLoader.cs:167-212`; `docs/setup/README.md:5`). Design-time flags disable compiler execution and analyzers, but Roslyn may materialize referenced generators when a navigation query needs a compilation (`MSBuildSolutionLoader.cs:39-51`; XML summary at `:15-18`).
- A request owns a resident Roslyn `Solution`/workspace for the selected solution path. The registry allows four resident solution instances by default and evicts idle entries after 45 minutes, on a five-minute tick; this is a count bound, not a memory or project/document bound (`ProjectRegistryOptions.cs:7-18`). It loads the whole solution via `OpenSolutionAsync` (`MSBuildSolutionLoader.cs:167-212`).
- Before a source snapshot is returned, structure freshness is recomputed. The fingerprint hashes the solution/project/configuration/import inputs, enumerates C# files under project and compile-glob roots, and records wildcard-import match sets (`SolutionStructureFingerprint.cs:22-75, 81-147, 150-177`). It catches many membership and same-timestamp edits, including nested imports and new files matching globs. A mismatch reloads the full solution (`ResidentSolution.cs:310-339`).
- Source/additional/analyzer-config documents are also read from disk on each snapshot refresh, grouped by physical path, hashed from read bytes, and applied to every Roslyn document sharing that path; this catches preserved-timestamp edits and shares reads for linked files (`ResidentSolution.cs:586-680`). On cold initialization, `CreateInitializedFileStates` reads documents once and `RefreshStaleness` reads them again (`ResidentSolution.cs:416-419`, `:548-570`). This is strong freshness evidence with an O(total tracked file bytes + project-tree scan) steady request cost and roughly doubled tracked-document reads on cold load/reload. The only timing fixture reports five runs without pass/fail thresholds and uses one tiny project (`tests/AiNetCodeNavigator.IntegrationTests/Workspace/SourceSnapshotIdentityMeasurementTests.cs:22-63`; `docs/development/build-and-tests.md:57`).
- Metadata PE/module images and source generator inputs are captured as immutable bytes before they enter the source identity. Source snapshot identity documents its tracked inputs and explicit blind spots: arbitrary external generator reads/environment are not tracked, and unaccountable inputs fail with `WORKSPACE_DIAGNOSTIC` (`docs/navigation/symbol-resolution.md:7-11`; `ResidentSolution.cs:455-499`).
- `browse_target(view=scope)` can report configured versus loaded target frameworks; it exposes frameworks missing from loaded Roslyn contexts and does not analyze them (`docs/navigation/get-index-scope.md:5-11`; `IndexScopeScanner.cs:68-120, 202-222`). `MSBuildStructureInputCollector` records configured `TargetFramework(s)` from project evaluation (`MSBuildStructureInputCollector.cs:30-55`). This is useful transparency, not proof that each configured TFM was loaded. Available workspace integration fixtures primarily use `net10.0` (`WorkspaceLoadingIntegrationTests.cs`, e.g. `:38, :58-59`); I found no explicit `net48`, Blazor/Razor, or WPF/XAML fixture in `tests/`, and therefore cannot claim those project types are verified.
- The scope inventory counts Roslyn project documents, including non-C# language documents, while the symbol-navigation analysis uses C# projects (`docs/navigation/get-index-scope.md:3-5`; `IndexScopeScanner.cs:68-75`). That can describe loaded project coverage but does not provide semantic navigation of `.razor` or `.xaml` artifacts. C# code-behind remains within ordinary C# navigation if MSBuildWorkspace loads it.
- MSBuild design-time scratch is isolated, owned, and cleaned on reload/disposal; output redirection outside the scratch root is rejected. This prevents Navigator's design-time writes into the source tree, while docs explicitly state arbitrary MSBuild targets are not sandboxed (`MSBuildSolutionLoader.cs:37-103, 167-212, 227-300`; `docs/mcp-host.md:17-23`). Hash-derived paths need MSBuild 17.10+ and can still encounter legacy Windows path limits in unusually long temp roots (`docs/mcp-host.md:17`).

## Review implications / recommendations

1. Measure before reworking correctness-first freshness. Add a representative workspace benchmark set (small, 100–300-project, multi-target, and legacy-style solution) measuring cold load, warm snapshot refresh, memory per resident solution, full fingerprint, and focused navigation. Preserve the existing same-timestamp edit test as a correctness gate. The current measurement is too small and has no thresholds to decide whether scans dominate agent latency. Low/medium implementation cost; low risk if measurement-only. Practical first experiment: run the current measurement and an added synthetic large fixture, recording bytes read, directories/files visited, and elapsed time separately.
2. Separate a cheap change-hint path from the authoritative snapshot validation only after measurements justify it. A bounded file watcher can mark candidate project/file inputs dirty and collapse repeated agent calls into one rescan; watcher overflow, missed events, symlink/out-of-root inputs, and exact correctness require a full-scan fallback or explicit strict mode. Never quietly return stale semantic bindings. Medium/high cost and correctness risk; technically feasible. Benchmark p50/p95 refresh latency and verify same-mtime edits, rename/add/delete, overflow/restart fallback.
3. Replace the fixed four-solution resident count with an observable memory-aware budget (for example estimated bytes/document count, eviction metrics, and configured cap), or at minimum expose resident solution/project/document counts and load timings. Four very different solutions are not equivalent memory units; large generators/compilations can create substantial memory pressure. Medium cost; uncertainty lies in estimating Roslyn memory accurately. Test an LRU workload with one large and several small solutions and measure process working set and reload frequency.
4. Improve analysis-target transparency and choice for multi-targeting. Always surface loaded contexts (TFM/config/platform) and configured-but-missing TFMs in a quick target summary; consider an explicit target-framework/configuration selector only if actual solutions show wrong-default-context errors. Loading all TFMs could multiply memory and compile costs, so do not make it the silent default. Medium cost; feasibility depends on MSBuildWorkspace's context behavior and project-reference graph. First test a small `net48;net10.0` project with divergent conditional APIs plus a project-reference edge and verify which contexts/compilations are loaded.
5. For Blazor/WPF, first add coverage samples to establish MSBuildWorkspace document behavior. If `.razor`/`.xaml` is absent from loaded semantic documents, a bounded generated-artifact/code-behind bridge may help; avoid claiming markup-level event/binding navigation without a parser/design-time model. Dedicated Razor/XAML semantic support is a separate significant feature, with risks around SDK/version-specific generation, design-time state, and false runtime claims.

## Explicitly unsupported inferences

- Do not describe `net48`, Blazor, or WPF source navigation as either supported or broken from this repository alone; it is configured to use local MSBuild and has no direct fixture evidence for those project types. Need representative user solutions to settle behavior.
- Do not recommend always loading every configured TFM: docs explicitly expose missing contexts, and complete multi-TFM loading can expand workspace memory and reference work substantially.
- Do not recommend build/run/test execution or live runtime tracing as a workspace freshness fix. The current loader is intentionally design-time/read-only; arbitrary MSBuild targets are executable and not sandboxed. Runtime behavior and dependency injection/reflection remain outside static Roslyn evidence.
- Do not remove full content hashing just to reduce latency. Same-timestamp replacement is explicitly supported and tested; any optimization must preserve a correctness path that detects it.
