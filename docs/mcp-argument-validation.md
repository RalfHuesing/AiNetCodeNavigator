# MCP Argument Validation

`McpArgumentValidationFilter` validates a registered SDK tool's incoming arguments before its handler is invoked. It reads the input schema from the matched `McpServerTool`, parses it with NJsonSchema, and validates the JSON argument object against that schema. The SDK schema is the source of truth, so required properties, primitive types, array items, enums, and declared constraints stay aligned with the tool advertised by the SDK.

The filter rejects unknown top-level arguments even if the SDK-generated schema does not explicitly close its root object. To preserve composed-schema semantics, it checks root property declarations through local references and `allOf`/`anyOf`/`oneOf` without rewriting the schema before NJsonSchema validates it. Nested objects follow their declared schema, including explicitly allowed `additionalProperties` schemas. Local references such as `$defs` are supported. External schema references are rejected so a request or schema cannot trigger a network fetch.

JSON Schema validation is followed by a binding compatibility check for SDK-backed methods. It uses `AIParameterNameAttribute` when the SDK registration explicitly renames a method parameter; otherwise it uses the CLR parameter name. `JsonSerializerOptions.PropertyNamingPolicy` affects object members and does not implicitly rename method parameter keys. The check catches values the schema accepts but the SDK binder cannot safely convert, including fractional or out-of-range C# integers. Cancellation is checked before validation and is passed through to the next request filter/handler. Invalid inputs return the standard `INVALID_ARGUMENT` error with a safe `fieldPath` (for example `$.options.label`, `$.options.first.label`, or `$.items[2]`) and a correction `nextAction`; ordinary dictionary keys retain their location through nested objects, arrays, and local references, while a missing field below an unsafe key uses `$` without echoing that key. The handler is not invoked. A malformed registered schema fails closed as `TOOL_SCHEMA_UNAVAILABLE`.

All filter-generated errors, including `TOOL_SCHEMA_UNAVAILABLE`, use valid `maxResponseBytes` and positive `maxResponseTokens` values supplied with the call. If the required error envelope cannot fit the token budget, the filter returns a sanitized MCP `InvalidParams` protocol error explaining that the token budget is too small; it does not return an over-budget text error or partial correction instruction. Other invalid budget values use the shared default error budget. After schema validation, the same request filter also checks error results returned by tool handlers against an explicitly requested byte/token budget and translates budget-specific `ArgumentOutOfRangeException` failures from early handler/route validation into sanitized `InvalidParams`. This covers errors returned before normal response formatting, such as unsupported scope/direction, invalid target routing, or assembly detail-level validation.

The production SDK server connects the filter through `WithRequestFilters(McpArgumentValidationFilter.Configure)`. Current eligible evidence includes transport-free `McpInputSchemaTests`, the original SDK-definition/binder checks in `IndexScopeContractTests.BrowseTarget_SdkDefinitionPublishesSharedRoutingParameters`, and per-tool handler validation. Retained in-memory MCP stream and child-process stdio cases are categorized `E2EIntegration`; their prior assertions are historical evidence and excluded from current completion gates. Parameter schemas remain defined by the original SDK tool methods rather than a copied test schema.
