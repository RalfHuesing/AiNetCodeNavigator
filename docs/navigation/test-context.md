# Static Test Candidates

`TestRecommendationBuilder` produces static test candidates from one source `Solution` and a resolved source symbol. It reuses that snapshot for semantic discovery and source references. In `get_context`, the `tests` section searches the full source solution independently of the optional usage scope, which applies only to the `uses` section.

Direct candidates come from references from recognized test methods to the selected declaration, references to discovered interface or abstract implementations, and fixture names derived from the selected type or those implementation types. A reference is accepted only when Roslyn reports a non-candidate location, its `ReferencedSymbol.Definition` matches the selected symbol or a discovered implementation, and the syntax at that location binds to that exact symbol. Constructor references are related to a type only when the selected/discovered symbol is that type; a constructor selected as the target remains a constructor match. Ambiguous candidates and error-typed receivers are excluded. Test methods are recognized from supported xUnit, NUnit, and MSTest attributes.

Method recognition uses fully qualified metadata-backed framework types, traversing attribute base types and xUnit v3's `Xunit.v3.IFactAttribute` interface. Supported attributes are xUnit `Fact`/`Theory`, NUnit `Test`/`TestCase`/`TestCaseSource`, and MSTest `TestMethod`/`DataTestMethod`; MSTest also requires a recognized `TestClass` attribute on the containing type. Source-defined lookalikes, unrelated attributes with the same short name, and unbound attributes do not establish a test method. Custom attributes deriving from recognized metadata types are supported. Framework labels use this same classifier. Project/file/class naming conventions still identify test-code scope and name-derived fixture candidates; helpers in that scope are not thereby test methods.

Recognized methods remain candidates even when statically excluded. Each method exposes `activityStatus`: `active` means no recognized static exclusion or condition was found, `excluded` means a recognized whole-method or fixture exclusion was found, and `conditional` means activity depends on a condition or case selection. xUnit `Skip` and `Explicit=true` exclude a method; `SkipWhen`/`SkipUnless` are conditional, including when combined with `Skip`, while explicit exclusion takes precedence. NUnit and MSTest `Ignore`, NUnit `Explicit`, and NUnit fixture `Ignore`/`Explicit` are checked on the method and enclosing types as applicable, including derived attributes. NUnit per-case `Ignore`/`Explicit` and mixed active/excluded fixture instances are conditional rather than proof that the whole method is excluded. When multiple method test attributes exist, an active attribute takes precedence over conditional or excluded attributes unless a whole-method/fixture exclusion applies. Values come from bound attribute named arguments and corresponding constructor parameters; attribute constructor bodies, property implementations, runtime conditions, custom runners, and runtime discovery are not evaluated. These statuses do not prove execution or coverage.

The source `get_context.tests` section and Core builder support `testHelperDepth=0..2` (default one). Zero retains direct and name-derived candidates. A request-local breadth-first walk follows up to that many intermediate source helper methods or constructors, with cycle detection and deterministic shortest paths. The final helper use of the target or a proven implementation may be a bound non-call use. Every preceding link must be an exact bound source invocation or constructor call; method groups, general member access, ambiguous candidates and unknown delegate targets do not form links. Virtual/interface calls record their static target and dispatch limitation. Direct evidence remains stronger than helper evidence. Explicit `testHelperDepth` requires the `tests` section and a source target, even when set to zero or one.

Each fixture exposes its source project name, project path and stable project identity, qualified class name, class reference when available, and source location. Methods also expose qualified names and their own file/line/column. Fixture-level `Evidence` distinguishes `target-name-heuristic` and `implementation-type-name-heuristic`; direct method-level `Evidence` distinguishes `direct-target-use` and `implementation-use`. Helper matches use `indirect-helper-use` with a shortest ordered static path: each step contains caller/target names, relationship kind, project path, reference location and available declaration references. Every evidence item includes its source symbol, project identity, file, line, column, and available source reference. Same-named types in different projects remain separate candidates. A name-derived fixture does not prove that its methods use or test the target. Results use `static-test-candidates-only` and make no execution or coverage claim.

Implementation expansion is capped at 64 symbols, reference inspection at 4,096 locations, and fixture collection stops after retaining the 257th distinct fixture (the first fixture beyond the 256-entry threshold). Core helper expansion is capped at 200 non-test helper members for the whole request, shared across target and implementation seeds. Reference inspection and locally reused reference evidence are likewise shared across direct and helper discovery. The Core payload and tests-section `analysis` report helper count/depth and its limit separately from implementation, reference-inspection, and candidate-expansion limits. A reached limit makes the analysis partial; it does not describe candidates beyond the inspected bound. Delivered fixtures/methods rank direct evidence before indirect evidence before name heuristics, Within each evidence group, fixtures sort by project identity, normalized file path and source line before class name; methods sort by their own normalized file path, line and column before method name.

`get_context.maxResults` is the fixture page size (1–100) when the `tests` section is selected, not an analysis limit. All collected fixtures remain available through that section's `resultCursor`, bound to the target, source snapshot, symbol query, selected sections, argument presence, helper depth, and page size. Read all outer `continuationToken` pages before following the section cursor; the shared continuation store preserves the completed response and snapshot. A changed query, page size, target, or source snapshot rejects the cursor.

The `tests` section returns totals, returned fixture count, `resultCursor`, and the scan-limit state from the Core payload. Source metadata reports `partial` when an analysis limit was reached and exposes the specific omission reason; `analysisNextAction` explains the fixed bound and suggests selecting a narrower symbol. Helper caps remain partial on the last domain page, after delivery continuation is exhausted. The candidate search filters generated documents unless `includeGenerated=true`.
