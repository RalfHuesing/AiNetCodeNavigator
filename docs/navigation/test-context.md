# Static Test Candidates

`TestRecommendationBuilder` produces static test candidates from one source `Solution`, a resolved source symbol, and its existing `AnalysisSymbolIdentity`. It reuses that snapshot for semantic discovery and source handoffs. In `get_context`, the `tests` section searches the full source solution independently of the optional caller scope, which applies only to the `callers` section.

Candidates come from three bounded sources: direct references from recognized test methods to the selected declaration, direct references to discovered interface or abstract implementations, and fixture names derived from the selected type or those implementation types. A reference is accepted only when Roslyn reports a non-candidate location, its `ReferencedSymbol.Definition` matches the selected symbol or a discovered implementation, and the syntax at that location binds to that exact symbol. Constructor references are related to a type only when the selected/discovered symbol is that type; a constructor selected as the target remains a constructor match. Ambiguous candidates and error-typed receivers are excluded. The scanner does not follow helper calls. Test methods are recognized from supported xUnit, NUnit, and MSTest attributes.

Each fixture exposes its source project name and stable project identity, class handoff, and source location. Fixture-level `Evidence` distinguishes `target-name-heuristic` and `implementation-type-name-heuristic`; method-level `Evidence` distinguishes `direct-target-use` and `implementation-use`. Every evidence item includes its source symbol, project identity, file, line, column, and available source handoff. Same-named types in different projects remain separate candidates. A name-derived fixture does not prove that its methods use or test the target. Results use `static-test-candidates-only` and make no execution or coverage claim.

Implementation expansion is capped at 64 symbols, reference inspection at 4,096 locations, and fixture collection stops after retaining the 257th distinct fixture (the first fixture beyond the 256-entry threshold). The payload reports implementation, reference-inspection, and candidate-expansion limits separately. A reached limit makes the analysis partial; it does not describe candidates beyond the inspected bound. Results are sorted by project identity, file, declaration, and method location before collection limits are applied.

`get_context.maxResults` is the fixture page size (1–100) when the `tests` section is selected, not an analysis limit. All collected fixtures remain available through that section's `resultCursor`, bound to the target, source snapshot, symbol query, selected sections, argument presence, and page size. Read all outer `continuationToken` pages before following the section cursor; the shared continuation store preserves the completed response and snapshot. A changed query, page size, target, or source snapshot rejects the cursor.

The `tests` section returns totals, returned fixture count, `resultCursor`, and the scan-limit state from the Core payload. Source metadata reports `partial` when an analysis limit was reached and exposes the specific omission reason; `analysisNextAction` explains the fixed bound and suggests selecting a narrower symbol. The candidate search filters generated documents unless `includeGenerated=true`.
