# Dependency Graph Core Scanner

`DependencyGraphScanner.ScanSolutionAsync` reports declared project references plus namespace, file, and type edges inferred from source type usages. File and namespace edges carry both project names, so identical relative paths or namespace names in different projects remain distinguishable. `TypeDependencies` preserves the source and target type IDs and names, projects, files, and traversal depth. Type IDs include assembly identity, and multiple types in one file remain separate graph nodes.

The scanner recognizes identifier, generic, and qualified type syntax through Roslyn semantic symbols. External metadata types, including BCL and package types, do not create namespace, file, or type edges. Partial source types use the syntax location containing the reference to retain the relevant source file.

Documents are processed in deterministic project-name and path order. `MaxDocuments` defaults to 1000 and is capped at 1000. `DocumentOffset` selects the first document in a batch; `NextDocumentOffset` is the cursor for the next call. `IsComplete` is true only when a response starts at offset zero and covers the remaining document list without errors or depth clamping. Later cursor pages stay marked partial because the Core API does not retain prior batches; callers can aggregate their type edges and verify that the final cursor is null. An offset past the end throws `ArgumentOutOfRangeException`.

`TargetFilePath` and `TargetTypeName` select a source file or fully qualified type as the traversal center; they are mutually exclusive. `Direction` is `Outgoing`, `Incoming`, or `Both`. `Depth` is clamped to 1–3 and the result exposes requested/effective depth and `IsDepthClamped`. Each edge keeps the source type, so callers in the same file remain distinct. A targeted `ScanSolutionAsync` call traverses only its current document batch; while `NextDocumentOffset` is present, results are partial and `IsComplete` is false.

For target traversal across document batches, scan each batch without target filters and pass every document and relationship page to `DependencyGraphTraversal.MergeAndTraverse`. The merger checks cursor continuity, combines direct type edges across batches, then applies the target, direction, and depth to the merged graph. Missing document or relationship pages set `ContinuationInputIncomplete` and keep `IsComplete` false. Traversal visits at most 200 types by default (`MaxNodes`), with a hard cap of 200; `VisitedTypeCount`, `NodeLimitReached`, and `HiddenTypeDependencyCount` describe the cutoff. A node cap or depth clamp keeps `IsComplete` false.

Relationship collections are paged independently with the same `Offset` and `PageSize`; page size defaults to 100 and is capped at 500. `Offset` must be nonnegative, `PageSize` and `MaxDocuments` must be positive, and a null solution throws `ArgumentNullException`. Cancellation propagates. The `Total*DependencyCount` values describe the relationship set for the current document batch, and the `HasMore*Dependencies` fields indicate additional relationship pages. `IsTruncated` and `IsComplete` also account for a nonzero relationship offset, document batches, depth or node limits, missing merge input, and document errors. Recoverable errors identify the project and document while retaining successfully analyzed results. Clamp metadata records page or document limits reduced to their hard caps.

The Core scanner does not provide tool-level production/test scope, generated-file filtering, or handoff rendering; those remain integration-layer responsibilities.
