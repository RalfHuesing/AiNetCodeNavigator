# Dependency Graph Core Scanner

`DependencyGraphScanner` collects source type-reference facts and project references, then projects them into the existing project, namespace, file, and type relationship payloads. A collection records exact source type ownership, eligible document coverage, successful collection coverage, and recoverable per-document errors. It retains scalar navigation facts rather than `Compilation` or symbol objects.

The scanner exposes `CollectAsync` and `Project` internally so callers can reuse one collection for different relationship pages or traversals. Collection orders documents by canonical owner project path and owner-context fingerprint, then by canonical document path, name, stored folders, source kind, and text hash. Each `(ProjectId, DocumentId)` is collected at most once per collection. Compilations are acquired once per participating project in that collection. A collection processes documents in internal batches of at most 1,000; that batch size does not cap the full collection.

The public Core `ScanSolutionAsync` keeps its bounded document-window contract: `MaxDocuments` is capped at 1,000, and `DocumentOffset` / `NextDocumentOffset` identify any remaining window. It collects its selected window once before producing its requested relationship page. `Offset` and `PageSize` page the projection and do not trigger semantic recollection within that call. A response is complete only when the selected window covers the eligible document set without errors, depth clamping, or other reported limits.

The MCP `dependency_graph` handler validates a source or assembly root, collects its selected source documents once, and projects the requested relationship page from that collection. Source requests drain the full eligible document set internally, including sets larger than 1,000; internal collection windows do not become public cursors. The response reports the eligible document total and successfully covered document count, starts at document offset zero, and has no next document offset when full collection finishes. Relationship `maxResults` limits the projected response, while response-size continuation handles delivery of an already computed result.

Selecting a source symbol resolves its exact owner-bound type identity. Selecting a file first matches its canonical physical path against all loaded regular and source-generated documents, before scope or generated-document filtering. A unique file contributes every declared named type as a root, including nested types and edge-free types; partial declarations contribute their other eligible declaration documents. A file with no named types remains a valid root with no type edges. No match or multiple owners returns `INVALID_ARGUMENT` at `$.filePath`; ambiguous results list owning project paths in ordinal order and direct the caller to discover a unique owner-bound symbol reference. Scope and generated filters select collection documents and do not silently erase proven dependency endpoints.

Type-node identity includes the canonical owning project path, its current owner-context fingerprint, and the original type identity. Equal display names in different project contexts remain separate. Equal directed type-edge keys choose their representative from the deterministic document order and file paths. Traversal orders candidate edges by exact type IDs and file paths, applies the same depth and node limits to file and symbol roots, and derives namespace and file summaries from the selected type edges. Project-reference summaries describe the loaded solution independently of the type roots.

Incoming and both-direction MCP requests collect full eligible-document coverage before traversal, so a partial document window cannot be treated as evidence that no incoming edge exists. Recoverable collection errors preserve successful edges and appear in `Errors` with the `scannerErrors` omission. A failed document does not count as successfully covered. Cancellation propagates without returning a successful partial payload. `DocumentLimitReached` and `continuationInputIncomplete` describe real missing required coverage or input; output-page truncation remains separate.

For assembly targets, symbol and file roots are restricted to the materialized decompiled source. The separated collection and projection path preserves the selected assembly owner when formatting visible edge references. Metadata nodes without a verified owner receive no assembly reference. The scanner recognizes identifier, generic, and qualified type syntax through Roslyn semantic symbols. External metadata types, including BCL and package types, do not create source type edges.

`ScopeType` filters production or test documents, and generated documents are excluded by default unless `IncludeGenerated` is true. `Depth` is clamped to 1–3 and the result reports requested and effective depths. Traversal admits at most 200 exact type nodes. `VisitedTypeCount`, `NodeLimitReached`, and `HiddenTypeDependencyCount` describe that cutoff. Direct Core scanning retains its window/page metadata; the MCP handler completes internal collection before returning the projected graph. See [Shared Symbol Resolution](symbol-resolution.md) for owner coordinates.
