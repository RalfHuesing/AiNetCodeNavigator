# Dependency Graph Core Scanner

`DependencyGraphScanner` collects source type-reference facts and project references, then projects them into the existing project, namespace, file, and type relationship payloads. A collection records exact source type ownership, eligible document coverage, successful collection coverage, and recoverable per-document errors. It retains scalar navigation facts rather than `Compilation` or symbol objects.

The scanner exposes `CollectAsync` and `Project` internally so callers can reuse one collection for different relationship pages or traversals. Collection orders documents by canonical owner project path and owner-context fingerprint, then by canonical document path, name, stored folders, source kind, and text hash. Each `(ProjectId, DocumentId)` is collected at most once per collection. A collection job acquires each participating project's compilation once. A collection processes documents in internal batches of at most 1,000; that batch size does not cap the full collection.

The public Core `ScanSolutionAsync` keeps its bounded document-window contract: `MaxDocuments` is capped at 1,000, and `DocumentOffset` / `NextDocumentOffset` identify any remaining window. It collects its selected window once before producing its requested relationship page. `Offset` and `PageSize` page the projection and do not trigger semantic recollection within that call. A response is complete only when the selected window covers the eligible document set without errors, depth clamping, or other reported limits.

The MCP `dependency_graph` handler accepts `level=type|file|namespace|project`, defaulting to `type`, and delivers only that selected relationship list and its totals. Type/file/namespace views validate a source or assembly root, collect their selected source documents once, and project the requested relationship page from the admitted type traversal. A member root selects dependencies of its owning type rather than a method-call graph. File and namespace projections retain a deterministic representative navigation location (file, line, column and endpoint project identities); it is one observed cause, not the only cause. Source incoming/both requests drain the full eligible document set internally, including sets larger than 1,000; internal collection windows do not become public cursors. Cold outgoing requests collect only eligible declaration documents of admitted types that need expansion. Depth 1 collects root declarations, including all eligible partial declarations, and deeper requests expand exact destination owners breadth-first while leaving terminal-depth declarations unscanned. A full resident collection serves outgoing projection directly. The response reports the eligible document total and successfully covered required-document count, starts at document offset zero, and has no next document offset after collection finishes. An intentionally unused outgoing subset creates no document-limit omission. Relationship `maxResults` limits the projected response, while response-size continuation handles delivery of an already computed result.

Project view is source-only and traverses existing loaded `ProjectReference` facts without semantic document dependency collection. It resolves the exact file or source symbol/member owner first; linked files with several loaded owners fail with sorted owner candidates, and a unique empty file remains a valid root. Explicit `scopeType` or `includeGenerated` is invalid even when set to `all` or `false`, because these document filters do not affect evaluated project references. Assembly project requests fail at `$.level`.

The project response keeps a separate compact `root` even without edges. `projectDependencies` carry directed endpoint IDs, minimum observed traversal depth and `origin=ProjectReference`; `projects` contains identities of the delivered edges' participating endpoints. Each identity carries the actual loaded `ProjectId`, name, canonical physical project path when available, and current owner-context fingerprint. Equal names or physical paths do not collapse distinct loaded contexts. Outgoing follows references, incoming follows referencing projects, and both unions the two directed walks without alternating directions. Depth is 1–3; cycles deduplicate directed edges. The shared traversal admits at most 200 projects including the root, and reports visited count, effective node limit, node-limit omissions and hidden edge count. `maxResults` bounds displayed edges; total, `hasMore`, `isTruncated` and `isComplete` distinguish that display limit from complete analysis. Repeat with a larger supported limit or narrower direction/depth when necessary; existing outer response pages deliver the stored result without another graph cursor.

For source requests, the host runtime retains only successful per-document scalar collection facts. A bucket is identified by the canonical target path, the freshly validated private snapshot ticket, `ScopeType`, and `IncludeGenerated`; root, direction, depth, level, relationship page, and response budgets affect projection only. Representative evidence strings participate in the same strict UTF-8 accounting and interning. A warm request with resident facts performs no semantic document scans. A changed source snapshot receives a new ticket, so preserved timestamps do not make old facts reusable. Cache misses fill the current bucket's missing documents, and recoverable document failures remain visible in that response and are retried on a later request. Resident facts use a process-local LRU bounded to four buckets, 32 MiB, and ten minutes of idle time. Accounting uses strict UTF-8 byte lengths for distinct ordinal strings, plus 17 bytes of bucket-key overhead and 64 bytes per successful document-coverage or dependency-edge record; an individual fact plus its bucket key that cannot fit by itself is returned to its caller without admission or eviction of unrelated data. An admissible fact joins the destination bucket under deterministic LRU eviction; if that destination is evicted, admission recomputes it from the new fact alone. Cache eviction leaves collections already held by a request valid. When a resident source owner retires, the runtime removes its retained buckets and drains its old-ticket jobs before disposing the resident solution; an overlapping newer snapshot ticket remains independent. `ApplicationStopping` cancels navigation operations and cache jobs. Runtime disposal drains navigation operations, awaits remaining cache cleanup, then releases resident solutions.

The source cache does not retain Roslyn symbols or handoff formatters. It stores scalar declaration coordinates needed to resolve only the exact owners of edges visible in the current projection, using the current solution and owner-context fingerprints. Assembly relationship scans remain one-shot and do not use the source cache.

Selecting a source symbol resolves its exact owner-bound type identity. Selecting a file first matches its canonical physical path against all loaded regular and source-generated documents, before scope or generated-document filtering. A unique file contributes every declared named type as a root, including nested types and edge-free types; partial declarations contribute their other eligible declaration documents. A file with no named types remains a valid root with no type edges. No match or multiple owners returns `INVALID_ARGUMENT` at `$.filePath`; ambiguous results list owning project paths in ordinal order and direct the caller to discover a unique owner-bound symbol reference. Scope and generated filters select collection documents and do not silently erase proven dependency endpoints.

Type-node identity includes the canonical owning project path, its current owner-context fingerprint, and the original type identity. Equal display names in different project contexts remain separate. Equal directed type-edge keys choose their representative from the deterministic document order and file paths. Traversal orders candidate edges by exact type IDs and file paths, applies the same depth and node limits to file and symbol roots, and derives namespace and file summaries from the selected type edges. Broad Core window payloads retain their loaded-solution project-reference summaries for the existing merge contract; the public project view instead follows its exact root owner as described above.

Outgoing scheduling uses the common traversal admission order and node cap before requesting declaration-document work. Shared documents, cycles and failed needs are attempted at most once per request; successful cached facts remain usable while another request fills broader coverage. Unrelated types in a collected document contribute facts without becoming symbol-root seeds. Unknown declaration ownership reports continuationInputIncomplete and directs rediscovery of a unique owner-bound declaration. Incoming and both-direction MCP requests collect full eligible-document coverage before traversal, so a partial document window cannot be treated as evidence that no incoming edge exists. Recoverable collection errors preserve successful edges and appear in `Errors` with the `scannerErrors` omission. A failed document does not count as successfully covered. Cancellation propagates without returning a successful partial payload. `DocumentLimitReached` and `continuationInputIncomplete` describe real missing required coverage or input; output-page truncation remains separate.

For assembly targets, symbol and file roots are restricted to the materialized decompiled source. The separated collection and projection path preserves the selected assembly owner when formatting visible edge references. Metadata nodes without a verified owner receive no assembly reference. The scanner recognizes identifier, generic, and qualified type syntax through Roslyn semantic symbols. External metadata types, including BCL and package types, do not create source type edges.

`ScopeType` filters production or test documents, and generated documents are excluded by default unless `IncludeGenerated` is true. The MCP rejects depth outside 1–3; direct Core window scans retain their depth-clamping contract and report requested and effective depths. Traversal admits at most 200 exact type nodes. `VisitedTypeCount`, `NodeLimitReached`, and `HiddenTypeDependencyCount` describe that cutoff. Direct Core scanning retains its window/page metadata; the MCP handler completes internal collection before returning the projected graph. See [Shared Symbol Resolution](symbol-resolution.md) for owner coordinates.
