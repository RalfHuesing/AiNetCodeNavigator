# Resolve Type Origin

The public `resolve_type_origin` tool accepts exactly one non-empty `symbolIdentifier` or `typeName` and routes by the target: a `.sln`/`.slnx` source solution or a managed `.dll`/`.exe` assembly. A source reference retains its exact owning project; ambiguous names return a typed resolution error. See [Shared Symbol Resolution](symbol-resolution.md) for reference rules.

Assembly origin lookup searches the root and its loaded reference candidates. A returned proven DLL path remains usable even when reference coverage is incomplete. In that case, `omissions` names `incompleteReferenceSearch` (plus `referenceDepthLimit` when applicable); `isAmbiguous=false` means the known candidates have one origin, not that omitted assemblies cannot contain another declaration. The recovery action advises restoring unavailable references and repeating the query, while acknowledging reference depth/node boundaries. Core root-only requests (`IncludeReferences=false`) do not inherit unrelated reference or decompiler omissions. Public assembly requests search references; decompiler diagnostics alone do not make that metadata search partial.

For a source type, the result reports its full type name, `assemblyOrigin: source`, owning `projectName`, project output assembly path when available, namespace, target solution path, and all source declaration locations with one-based line and column. This declaration result is complete for its reported owner and locations and does not perform a metadata search. Nested and generic metadata names use the same normalization and nested lookup as assembly type-origin resolution. If no source declaration matches, the scanner searches each project's resolved metadata references and reports the unique reference assembly path with `assemblyOrigin: reference`. Multiple same-named metadata types or an unproven assembly path are reported as ambiguous with candidate paths; no match returns `found: false` together with the searched assembly names. Source metadata lookup is always enabled.

Every source-target metadata result, including a positive or ambiguous result, reports `metadataSearchScope: loadedReferences` and `declaredReferenceCoverage: unknown`. The workspace can omit unavailable declared references before this search; the result does not identify individual missing DLLs or prove a complete reference closure. Its analysis metadata is partial with `omissions=declaredReferenceCoverageUnknown`. The recovery action advises restoring unavailable references and retrying; a proven returned owner remains usable. `found: false` means no match among the loaded candidates. For a found type, `isAmbiguous: false` means those known candidates have one origin. Completing all outer response pages completes delivery, not declared reference coverage. The existing owner, candidate paths and `searchedAssemblies` fields remain available.

For an assembly target, `ResolveTypeOriginScanner` searches the target assembly and its resolved references. It reports local, reference, framework, package, or ambiguous origins and uses a metadata reference path only when its assembly identity matches the resolved type. A `symbolIdentifier` may be a raw declaration name, documentation ID, or source position resolved in the selected target's decompiled source, or a stable reference resolved only in the supplied owner. Malformed references never fall back to raw-name matching. Missing assembly types return `SYMBOL_NOT_FOUND`.

Source handlers have direct SDK-handler coverage without a server or transport. It checks missing declared HintPaths and available metadata owners through the standard loader, preserves the metadata boundary across outer pages, and keeps direct source ownership complete. Core coverage checks source-origin project identity, nested generic source and metadata types, ambiguous metadata candidates, the `System.String` framework reference, and exact DLL path selection for same-named package assemblies with different versions. The public assembly path has separate integration coverage. Source byte- and token-limited projections are independently reconstructed from the same broad handler query; remaining assembly-specific relationship obligations are tracked separately in [MCP navigation registration status](mcp-registration-status.md).
