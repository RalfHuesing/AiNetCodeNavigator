# Resolve Type Origin

The public `resolve_type_origin` tool accepts exactly one non-empty `symbolIdentifier` or `typeName` and routes by the target: a `.sln`/`.slnx` source solution or a managed `.dll`/`.exe` assembly. A source reference retains its exact owning project; ambiguous names return a typed resolution error. See [Shared Symbol Resolution](symbol-resolution.md) for reference rules.

For a source type, the result reports its full type name, `assemblyOrigin: source`, owning `projectName`, project output assembly path when available, namespace, target solution path, and all source declaration locations with one-based line and column. Nested and generic metadata names use the same normalization and nested lookup as assembly type-origin resolution. If no source declaration matches, the scanner searches each project's resolved metadata references and reports the unique reference assembly path with `assemblyOrigin: reference`. Multiple same-named metadata types or an unproven assembly path are reported as ambiguous with candidate paths; no match returns `found: false` together with the searched assembly names. Source metadata lookup is always enabled.

For an assembly target, `ResolveTypeOriginScanner` searches the target assembly and its resolved references. It reports local, reference, framework, package, or ambiguous origins and uses a metadata reference path only when its assembly identity matches the resolved type. A `symbolIdentifier` may be a raw declaration name, documentation ID, or source position resolved in the selected target's decompiled source, or a stable reference resolved only in the supplied owner. Malformed references never fall back to raw-name matching. Missing assembly types return `SYMBOL_NOT_FOUND`.

Source handlers have direct SDK-handler coverage without a server or transport. It checks source-origin project identity, nested generic source and metadata types, ambiguous metadata candidates, the `System.String` framework reference, and exact DLL path selection for same-named package assemblies with different versions. The public assembly path has separate integration coverage. Source byte- and token-limited projections are independently reconstructed from the same broad handler query; remaining assembly-specific relationship obligations are tracked separately in [MCP navigation registration status](mcp-registration-status.md).
