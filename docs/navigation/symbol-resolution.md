# Shared Symbol Resolution

The existing `handoffId`, `fromHandoffId`, and `toHandoffId` fields carry stable declaration references; JSON field names, casing, null behavior, and renderer formats remain the same. `docCommentId` remains descriptive metadata, and there is no second stable-ID field. Source references have the form `src:<project-path>|<declaration-id>`; assembly references have the form `asm:<simple-name>|<declaration-id>`. The codec escapes `%`, `|`, and ASCII spaces as `%25`, `%7C`, and `%20`, and decodes those escapes once. References identify declarations, not snapshots or historical entities.

For source, `<project-path>` is the canonical relative path of a loaded project from the nearest `.git` working-directory root, or from the selected solution directory when no Git marker exists. The declaration ID is the exact Roslyn documentation declaration ID. Resolution selects that loaded project first and then requires one exact declaration-ID round-trip in its current compilation. If the same physical project path identifies multiple loaded Roslyn contexts, resolution returns `AMBIGUOUS_SYMBOL` and reports the owner path, project name, target framework, configuration, and platform for each context. Recovery uses a solution/load configuration with one intended context; this wire reference does not add a TFM or candidate-ID selector. For assemblies, the simple name comes from metadata and resolution occurs only in the supplied target assembly's current owner generation. Keep the exact returned `targetPath`/`ownerTargetPath` with an assembly reference, especially when a result belongs to a referenced DLL. An evicted owner is reopened through normal target loading. Selecting a different same-name DLL deliberately selects that target.

An unchanged declaration reference remains usable after body edits, unrelated edits, project-option changes, or a server restart when the same owner coordinate and declaration ID still select exactly one declaration. A rename, signature change, project move, or missing declaration requires fresh discovery. Retained response pages and analysis evidence remain tied to their reported snapshots; assembly relationship work also retains its existing generation leases and owner provenance. Body windows resolve the current declaration text. Do not combine windows read from different reported snapshots as one body.

Input routing examines the original argument before the normal discovery-name cleanup. For a reference, the resolver trims only outer ASCII spaces, strips at most one matching enclosing pair of backticks, double quotes, or single quotes, trims outer ASCII spaces again, then validates the remaining payload. It does not normalize the path or declaration ID. Prefixes are recognized case-insensitively for routing, while canonical wire prefixes are lowercase. A reference has one unescaped `|`, two non-empty components, uppercase canonical escapes, and a declaration ID beginning with `T:`, `M:`, `P:`, `F:`, or `E:` followed by a non-empty value. Only `%`, `|`, and ASCII space are escaped as `%25`, `%7C`, and `%20`; decoding happens once. Controls, malformed escapes, noncanonical encoding, and malformed `src:`, `asm:`, legacy `h:`, or internal `i:` identifiers return `INVALID_SYMBOL_REFERENCE`; they never fall through to name or location discovery. Non-empty `H:/...`, `H:\...`, `I:/...`, and `I:\...` inputs keep the existing physical-path route, subject to host path validation. Existing names, raw documentation IDs, and source locations remain discovery inputs.

The selected owner and all declaration matches must be unique. A malformed reference returns `INVALID_SYMBOL_REFERENCE`; a missing or renamed declaration returns `SYMBOL_NOT_FOUND`; a wrong origin or source owner returns `TARGET_MISMATCH`; an ambiguous owner or declaration returns `AMBIGUOUS_SYMBOL`; an unrepresentable owner coordinate returns `UNSUPPORTED_IDENTIFIER`; and an unavailable required source compilation returns `WORKSPACE_DIAGNOSTIC`. Each response's recovery action directs callers to rediscover on the intended current target or use available raw-location navigation. These errors do not imply that an unchanged reference became stale because of content edits.

Some declarations cannot be represented by a unique canonical reference, including local functions, anonymous or synthesized declarations, file-local declarations whose IDs do not round-trip uniquely, and declarations without a stable owner coordinate. Their raw name, location, body, and owner metadata remain available where supported. The existing stable-reference availability flags are false, follow-up-tool lists are empty, and nullable reference fields retain their current null/omission behavior. Renderers omit the reference fragment; no location-based or allocated-ID fallback is emitted. Body availability remains independent: a declaration with readable text can still report an available body even when no stable reference can be represented. Existing physical-path selectors keep their prior solution/decompiler-relative base. A source reference supplied to `get_file_skeleton.filePaths` resolves to every declaring regular or generated document, including partial declarations; that tool has no scope/generated-source filter. Tools that expose those filters resolve the exact owner and declaration first, then apply the requested filters.

Source raw discovery accepts Roslyn documentation IDs, supported declaration names/signatures, and existing source-location selectors. Assembly raw discovery is limited to the selected decompiled owner except where a tool explicitly searches resolved referenced owners. These inputs retain their existing ambiguity rules and are not additional stable IDs. The common Core resolver owns reference parsing; handlers and renderers pass reference strings through unchanged.
