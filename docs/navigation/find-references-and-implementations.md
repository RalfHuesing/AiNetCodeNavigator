# Find References and Implementations Core Engines

`FindReferencesResolver` uses Roslyn's solution-wide symbol reference search. The legacy overload searches direct references (depth 1); the depth overload follows caller symbols breadth-first, with depth clamped to 1–3 and a hard cap of 200 expanded symbols. A lower `maxNodes` value can narrow the node budget; higher values are clamped to 200. Each source location includes its relative file path, one-based line and column, source snippet, project name, enclosing symbol name, depth, evidence kind, and the symbol whose references were searched. Evidence distinguishes calls, member access, statically selected virtual/interface targets, possible bindings, and unresolved bindings. When a canonical source identity is available, both the enclosing and reached-from symbols include opaque `h:` handoffs that resolve to declarations in the correct project. Visited symbols are de-duplicated to stop cycles.

`FindImplementationsResolver` behavior is provided by `FindReferencesResolver.FindImplementationsAsync`. For interface types it returns implementing types across the solution; for classes it returns direct and indirect derived types. For interface methods it returns implementing members, and for virtual, abstract, or override methods it returns overrides. Entries include a source location, signature, project name, and an opaque source handoff when available.

Both resolvers sort results deterministically and normalize `maxResults` to at least one. Impact projects the same bounded reference traversal, so recursive sites, same-line columns, evidence kinds, and reached-from identity agree. Separate calls on one line remain separate entries in both results. `FindReferencesResult.TotalCount` counts discovered call sites before the display limit; `IsTruncated` reports display-limit truncation, while `IsTruncatedByNodeLimit` and `IsDepthClamped` report traversal limits. `IsComplete` is false when any of these limits prevent the requested traversal. `EffectiveNodeLimit` reports the applied node cap. `FindImplementationsResult.TotalCount` reports the full number of implementations before limiting and `IsTruncated` reports display-limit truncation. Unsupported implementation targets (such as structs and non-virtual concrete methods) return an empty result with `IsSuccess == false` and an explanatory `ErrorMessage`; a supported symbol with no results returns `IsSuccess == true`. Null symbols and solutions throw `ArgumentNullException`; a node limit below one throws `ArgumentOutOfRangeException`. Cancellation is passed through Roslyn searches and checked while collecting locations.

These Core APIs take an already-resolved Roslyn symbol, so unknown names, ambiguous identifiers, and invalid or stale handoffs are reported by the shared symbol-resolution layer before calling them. The public handlers accept `scopeType` (`all`, `production`, or `tests`) and `includeGenerated` (false by default). They filter source locations before totals and result limits. Direct source-handler tests exercise normal results, source-specific errors, response budgets and visible handoffs to body consumers. `find_references` verifies callsite columns, reached-from provenance, same-line calls and reconverging paths; `get_type_hierarchy` and `find_implementations` verify totals before caps and project-qualified generic declarations. Assembly targets for `find_implementations`, `find_references`, and `get_call_tree` resolve owner-bound assembly handles and reject foreign targets. Public tests follow an interface type implementation, interface method implementation, interface property implementation, virtual method override, and virtual property override to the owning assembly body. They also follow an incoming reference and incoming/outgoing call-tree node from `BetaInvoker.Invoke` to its body, and an impact caller location from `PagedBeta.ReadBeta` through `BetaInvoker.Invoke` to its body. A genuine source-origin handoff sent to an assembly relationship route returns `TARGET_MISMATCH`.

For assembly `find_references`, `includeReferences=true` scans the bounded resolved reference closure and follows caller declarations across owners to the requested depth (capped at three). Each returned assembly location includes its owner's canonical `ownerTargetPath`, so the matching handle can be passed to an owner-aware follow-up. Relationship results retain evidence kinds through owner projection. The public Root → B → C regression passes a C-owned method handle to a search rooted at A, verifies B and C callers, then follows A.Run at depth 2 to A's body. It also verifies a complete depth-3 query when the fixture has no further callers. Type references resolve to the declaring B type. Foreign owner handles are rejected and same-path replacement makes prior handles stale. For source results, duplicate elimination retains `Document.Project.Id` as an internal owner key, so linked documents with identical names, assembly names, and symbol IDs remain separate; stable ordering uses the owning project path. Assembly caller handles are generated only after the globally visible locations are selected. Assembly `get_call_tree`, symbol-mode `get_impact`, and the Caller/Impact sections of `get_assembly_context` use the same owner-specific closure session. Public tests follow incoming C.Read → B.Run → A.Run and outgoing A.Run → B.Run → C.Read, including owner-target body follow-ups; a depth-2 context is complete for this fixture. Closure, depth, node, or output bounds and unresolved owners remain explicitly incomplete.

Assembly relationship consumers also accept raw names, documentation IDs, and source positions. Without `includeReferences`, raw resolution is limited to the selected binary's own decompiled source. When `includeReferences=true`, raw resolution searches the current reference owner leases before starting the relationship query. Ambiguous raw names return selectable owner paths and owner-bound handles; the stdio fixture follows a B-owned `Run` candidate to B's body and checks that raw C.Read resolves from A for references, call tree, impact, and assembly context. Invalid positions in a known referenced source preserve `INVALID_ARGUMENT`, and incomplete or unavailable owner scans do not yield a supposedly unique raw selection. Opaque handoffs retain strict owner validation.
