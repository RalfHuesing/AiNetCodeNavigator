# Find References and Implementations Core Engines

`FindReferencesResolver` uses Roslyn's solution-wide symbol reference search. Depth 1 returns direct references; depths 2–3 follow caller symbols breadth-first. A lower `maxNodes` value can narrow the node budget; higher values are clamped to 200. Each source location includes its relative file path, one-based line and column, source snippet, project name, enclosing symbol name, depth, evidence kind, and the symbol whose references were searched. Evidence distinguishes calls, member access, statically selected virtual/interface targets, possible bindings, and unresolved bindings. When an exact canonical source identity is available, the enclosing and reached-from symbols include stable references that resolve to declarations in their owning projects. Visited symbols are de-duplicated to stop cycles.

`FindImplementationsResolver` behavior is provided by `FindReferencesResolver.FindImplementationsAsync`. For interface types it returns implementing types across the solution; for classes it returns direct and indirect derived types. For interface methods it returns implementing members, and for virtual, abstract, or override methods it returns overrides. Entries include a source location, signature, project name, and a stable source reference when available.

Both resolvers sort results deterministically and normalize Core `maxResults` to at least one. Optional [reference summaries](reference-summary.md) aggregate the same bounded traversal before display paging. Recursive sites, same-line columns, evidence kinds, and reached-from identity remain available; separate uses on one line remain separate entries. `FindReferencesResult.TotalCount` counts discovered reference sites before the Core display limit; node and depth bounds remain traversal limits, and `EffectiveNodeLimit` reports the applied cap. The source and direct assembly MCP routes collect discovered locations before applying their public `maxResults` page size, then expose every known entry over `resultCursor` pages. `includeReferences=true` remains bounded by owner-closure, depth, node, and unresolved-owner limits; those analysis limits are separately reported. `FindImplementationsResult.TotalCount` reports all implementations found by Core before its display limit. Unsupported implementation targets (such as structs and non-virtual concrete methods) return an empty result with `IsSuccess == false` and an explanatory `ErrorMessage`; a supported symbol with no results returns `IsSuccess == true`. Null symbols and solutions throw `ArgumentNullException`; a node limit below one throws `ArgumentOutOfRangeException`. Cancellation is passed through Roslyn searches and checked while collecting locations.

These Core APIs take an already-resolved Roslyn symbol, so unknown names, ambiguous identifiers, and invalid references are reported by the shared symbol-resolution layer before calling them. The public handlers accept `scopeType` (`all`, `production`, or `tests`) and `includeGenerated` (false by default), applying source filters before totals and paging. Relationship result cursors bind the target snapshot, query, scope, result section, and `maxResults` page size; a continuation can change response byte/token budgets, but changing the page size returns `RESULT_CURSOR_ARGUMENT_MISMATCH` and requires a fresh query. A cursor from a replaced target snapshot returns `STALE_SNAPSHOT`. Source and assembly handler contracts reconstruct direct references and implementations across pages. Each assembly reference retains its reported owner target. Traversal depth and node limits remain distinct from result-page availability. A source reference sent to an assembly relationship route returns `TARGET_MISMATCH`. See [Shared Symbol Resolution](symbol-resolution.md) for declaration reference lifetime and errors.

For assembly `find_references`, `includeReferences=true` scans the bounded resolved reference closure and follows caller declarations across owners to the requested depth (capped at three). Each returned assembly location includes its owner's canonical `ownerTargetPath`, so a returned reference can be passed to an owner-aware follow-up. Relationship results retain evidence kinds through owner projection. Source results keep `Document.Project.Id` as an internal owner key, so linked documents with identical names, assembly names, and symbol IDs remain separate; stable ordering uses the owning project path. Assembly caller references are created only after the globally visible locations are selected. Assembly `get_call_tree`, `find_references`, and the `callers` section of `get_context` use the owner-specific closure session. The context callers section returns direct incoming locations only; transitive traversal stays in call-tree and reference workflows. Closure, depth, node, or output bounds and unresolved owners remain explicitly incomplete. Reference lifetime and generation evidence are described in [Shared Symbol Resolution](symbol-resolution.md).

Assembly relationship consumers also accept raw names, documentation IDs, and source positions. Without `includeReferences`, raw resolution is limited to the selected binary's own decompiled source. When `includeReferences=true`, raw resolution searches the current reference owner leases before starting the relationship query. Ambiguous raw names return selectable owner paths. Invalid positions in a known referenced source preserve `INVALID_ARGUMENT`, and incomplete or unavailable owner scans do not yield a supposedly unique raw selection. The exact returned owner target is retained for assembly references.
