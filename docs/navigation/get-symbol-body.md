# Get Symbol Body

`SourceSymbolBodyResolver.Resolve` extracts the source declaration associated with a Roslyn symbol. The identifier-based `ResolveAsync` first uses the [shared symbol resolution contract](symbol-resolution.md); unresolved or ambiguous identifiers return a structured error and, for ambiguity, selectable candidates. The body result contains declaration text, source availability, total line count, displayed one-based line bounds, truncation state, documentation ID, and an optional source handoff. A partial method definition with an implementation resolves to the implementation declaration. Default interface methods with executable bodies remain available; abstract methods and properties, abstract interface members, and interface declarations report unavailable bodies.

`maxBodyLines` limits the output window and `startLine` selects its one-based starting line. Values below one are normalized to one. A window that exceeds the declaration returns a message with the total line count and does not throw. Truncated windows include a continuation marker and set `HasMore`. Each successful MCP item reports `Resolution status: resolved`, its displayed line interval, and either a complete-window action or its own next `startLine` and `maxBodyLines`. Continue with that item's handoff, omit `endLine`, and read every outer response page before requesting the next body window; this keeps the next interval executable even when the first request used an explicit `endLine`.

`ResolveBatch` applies the same window to each input symbol, preserves input order, and returns an empty result for an empty sequence. Metadata symbols without source syntax are retained as unavailable results with zero source lines, so they do not prevent other batch items from being returned. Passing a null symbol or null batch sequence throws `ArgumentNullException`.

The MCP host currently registers `get_symbol_body` for source and managed-assembly targets. Assembly handoffs from referenced assemblies must be called with the owner `targetPath` printed by the producer. Every item reports its own resolution status and recovery action. A mixed batch retains successful bodies and includes the failure code, hint, and rediscovery action for each failed item; an all-failed batch remains an MCP error while preserving details for every requested item. `HANDOFF_UNKNOWN`, `TARGET_MISMATCH`, `STALE_SNAPSHOT`, and `HANDOFF_OWNER_UNRESIDENT` distinguish unknown handles, another owner, a changed resident generation, and an owner session no longer resident. Recovery repeats discovery against the indicated current owner and uses only a newly returned handoff; no old body is offered as fallback. Assembly batches pin one target generation lease for their duration, including batches with raw identifiers and handoffs. `SourceToolsContractTests` verifies exact adjacent body-window intervals through completion, mixed-success versus all-invalid batches, and separate tight byte and token projections. It reconstructs the complete multi-page body and compares it exactly with the same broad-budget query after stripping page headers. Existing stdio fixtures cover source handles and the assembly Root → B → C closure, including live replacement and deletion; the new per-item recovery and eviction cases are verified through direct handler tests. E2E tests were excluded from this task's executed gates. See [MCP Host](../mcp-host.md) for the current contract limits.

For a managed-assembly target, the body tool also accepts a raw declaration name, documentation ID, `path:line`, or `path:line:column` within that target's decompiled source. A raw success returns its owner-bound `h:` and canonical owner `targetPath` in the response, so the caller can use the same identifier in another assembly consumer. Tests cover raw type and method IDs, a qualified method name, line-only and column positions, and a raw-body-handoff-to-class-structure roundtrip. A source `h:` passed to an assembly target remains `TARGET_MISMATCH`.
