# Assembly Navigation Core Scanners

The host's `AssemblyCallTreeClosureBuilder` constructs cross-owner call trees in separate owner-expansion, graph-merge, and global-projection phases. `RelationshipTools` owns the closure session lifetime, typed failures, rendering, and MCP response formatting. Both use `AssemblyHandoffFormatting` for the existing generation-bound owner handoff rules, and `AssemblyTools` reuses its source-ownership check when formatting assembly context handoffs.

The assembly scanners open a managed `.dll` or `.exe` through a resident, read-only decompilation session and use its in-memory Roslyn compilation. ILSpy opens the root PE and resolved dependencies with `PEStreamOptions.PrefetchEntireImage`, so their streams close after each image is loaded and resident sessions do not prevent a normal replacement or deletion. Sessions are reused by canonical target path and keep at most 32 resident targets; idle sessions expire after ten minutes and release their Roslyn snapshots. If all 32 sessions have active operations, acquisition of a new target fails with `ASSEMBLY_SESSION_LIMIT` and can be retried when an operation completes. Each operation holds a generation lease while it reads symbols. Before reuse, the session refreshes the target fingerprint and resolves and fingerprints the current reference set, so changed target or dependency files create a new effective generation and diagnostics. The decompilation cache is bound to that same reference-content snapshot for both reads and publishes; changed references cannot pair stale decompiled source with new Roslyn metadata. A failed refresh never serves the previous generation. If the exact target and reference snapshot of a retained generation are restored, that generation becomes eligible for reuse again with its original status and diagnostics. Scanners do not execute the target binary or modify the target file.

Assembly `inspect_assembly`, `find_symbol`, and the public `get_namespace_tree` type entries bind handoffs to the canonical owner path, owner PE SHA-256, resolved reference-snapshot fingerprint, current owner generation, and canonical documentation-comment ID. The reference fingerprint covers the resolved transitive assembly closure. Assembly `find_symbol` prints the owner `targetPath` beside each reference result so clients can pass the right binary to a follow-up. `AssemblySymbolHandoffResolver` restores opaque handles, verifies assembly origin, refreshes the owner target, validates its current root/reference generation identity, and resolves the declaration only in that target assembly. `get_symbol_body` and the advertised `get_class_structure` follow-up both check the supplied `targetPath` against the handle's owner. Unknown, source, foreign-target, stale, unreadable, and missing-symbol failures are typed MCP errors when every requested body fails; a mixed batch retains successful bodies and reports its failed identifiers as a truncated result. For assembly namespace entries, `get_symbol_body` and `get_class_structure` are tested follow-ups and return data from the owning binary. The assembly namespace tree is also a tested assembly handoff producer. Root-decompiled entries from `get_type_hierarchy` and `find_implementations` use the same canonical assembly owner, PE hash, reference snapshot, generation, and declaration ID; the public tests follow subtype and type/member implementation handles to the owning body and reject foreign target paths. `get_call_tree` and `find_references` route assembly handles through the selected decompiled source and prove owner-bound caller handles with incoming/outgoing and body roundtrips. Assembly `dependency_graph` resolves exact symbol/project or file/document targets against the selected decompiled source and emits endpoint handles only for owner-proven declarations on the visible result page; both endpoint handles were followed to their bodies. Source-origin or foreign-target handles fail with `TARGET_MISMATCH`. Assembly `find_references(includeReferences=true)` scans resolved referenced-assembly source and follows callers across owners to the requested depth (capped at three), returning handles with each actual owner's canonical target path. Root → B → C stdio tests follow callers through depth 2 to owner bodies and verify stale-owner rejection; the fixture's depth-3 query completes. Assembly `get_call_tree(includeReferences=true)` scans compatible source owners in the resolved closure, maps metadata graph nodes only when the full original PE identity and declaration resolve to one owner, and prints that owner's target path beside its handoff in ASCII and Mermaid output. In the direct Root → Bridge → Leaf test, the Leaf.Read handle from `find_symbol` reaches the Leaf body, while emitted Calltree caller handles for Bridge.Forward and Root.Run are followed using their displayed canonical target paths. The requested `topN` fanout is enforced globally after owner graphs merge; duplicate edges merge only when their source, destination, and dispatch kind agree. The global node and edge hard cap is 250, and nodes receive opaque handoffs only after final visible projection. Incoming C.Read → B.Run → A.Run and outgoing A.Run → B.Run → C.Read are followed to owner bodies at depth 2; owner/depth/output bounds and unresolved references remain explicitly incomplete. Symbol-mode `get_impact(includeReferences=true)` uses the shared bounded owner traversal, returns owner-bound caller handles with canonical target paths, and follows cross-owner results to their owner bodies. Known direct/transitive totals remain accurate when `maxResults` caps visible call sites. `get_assembly_context(includeReferences=true)` uses the same owner-scanning services for Callers and Impact; B.Run and C.LocalRun handles from both sections were followed to their actual owner bodies. The depth-2 Root → B → C fixture returns complete Caller and Impact sections with A.Run visible. `dependency_graph` has no `includeReferences` option. Unresolvable foreign metadata symbols receive no handoff.

The direct, transport-free `AssemblyToolsContractTests` exercises all 17 assembly-capable handler routes against generated managed assemblies and verifies normal owner results rather than loading/polling controls. Applicable handles emitted by namespace-tree, skeleton, call-tree (ASCII and Mermaid), implementation, impact, dependency-graph, inspection, and declaration-search results are followed through `get_symbol_body` using the same owner; extension results do not expose a handoff identifier. The Root → Bridge → Leaf test follows Leaf.Read to the Leaf body from `find_symbol`, then follows the emitted Bridge.Forward and Root.Run calltree caller handles using their displayed canonical owner paths. The namespace-tree handler converts its internal symbol identity to an opaque public `h:` handle before formatting, for both source and assembly targets. The assembly class-structure formatter sorts omitted/`lines` members by relative file path (`OrdinalIgnoreCase`), declaration start line, and name (`OrdinalIgnoreCase`) before applying `maxMembers`; the fixture's complete member sequence matches the source handler, while a separate Assembly-only cap-1 assertion confirms first-declared `Zulu` precedes later `Alpha`. Both direct and context class-structure results emit a member handle that resolves to its body. Every route receives a separate measured byte- and token-capped owner projection; if an observed projection is unfit, the exact offered minimum pair is retried. These all-route projections do not claim full-text reconstruction for all 17 routes; exact reconstruction is asserted for the named Inspect/Search and mixed Context cases, and for the separate 30-caller Impact contract.

The direct context tests compose Body, Class Structure, Callers, and Impact. A valid symbol resolves before a controlled fixture replacement with the same assembly name/version makes the real body scanner return `STALE_SNAPSHOT`; the overall context response remains an error with recovery guidance. New searches then resolve the added declaration and changed `Read` method in that replacement; both opaque handles reach the actual bodies, and the changed body contains the replacement's return value. A separate long-body case exercises a later outer page that cannot fit, retries its exact offered byte/token pair unchanged, then reconstructs all four sections and compares the complete text to the broad response. The deterministic test callback is internal, instance-scoped, and null on the normal host path. Hierarchy, method override, and property override handoffs are each followed to `get_symbol_body`.

The public `inspect_assembly` `continuationToken` accepts the scanner's `v1.<offset>.<binding>` domain cursor as well as the host's fixed-width decimal response-page token. Domain bindings include the canonical target, root hash, resolved reference-snapshot hash, and all query limits/filters. Complete any outer response-window pages before following the domain cursor. Domain-cursor replays return the same next page, and changed query arguments, targets, root contents, or resolved references fail as invalid arguments. Direct-handler inspection and search tests consume every domain page only after reconstructing that same page through all outer decimal-token pages, compare exact page text with the wide-budget query, and verify replay/binding plus truthful `maxFiles` final truncation. The command-scoped component gate also covers Root → B → C, reference replacement, missing references, stale handoffs, and exact-snapshot target restoration. Public stdio tests verify that A references B while B references C, `find_symbol(includeReferences=true)` emits C's owner path and handoff, the same handle roundtrips to C's body, and using A as the follow-up target returns `TARGET_MISMATCH`. They replace C at the same path while the host is active, require the old handle to fail with `STALE_SNAPSHOT`, require a new search/body to expose the replacement, then delete C without stopping the host. A fresh Root search reports no C match with `unresolvedReferences` and truncated completeness, and using the old C handoff through the live Root target fails without returning stale text.

Assembly symbol-input consumers accept raw declaration names, documentation IDs, `path:line`, and `path:line:column` against the selected materialized source. `get_symbol_body`, `get_class_structure`, hierarchy, implementations, dependencies, impact, references, call tree, type-origin, and symbol-composed assembly context use this owner-checked input path. Tools with `includeReferences=true` resolve raw symbols across the current owner leases; otherwise the raw search stays in the root assembly. Ambiguous cross-owner input reports each selectable owner path and opaque handoff. Successful raw body output includes its generated owner `h:` and `targetPath`. The Stdio regression follows a B.Run ambiguity candidate to B's body and a raw C.Read query from A through references, call tree, impact, and context; source/foreign/malformed handoffs remain strict errors. Owner scans with a failed or bounded reference scope do not return a falsely unique raw match.

The public `get_type_hierarchy` and `find_implementations` routes resolve assembly handles against the selected owner generation. The tested root-source cases include a derived type, interface implementation, interface method/property implementation, and virtual method/property overrides; each concrete subtype or implementation handoff was followed to the same assembly body. Metadata-only types do not receive source handoffs. Referenced-assembly source scanning remains open.

`AssemblyContextScanner.GetAsync` returns the assembly identity, analysis status, decompilation origin, namespace and type totals, reference totals, and diagnostics. `MaxResults` defaults to 100 and is capped at 1,000 for the namespace and type name lists. Reference details are omitted by default; `IncludeReferences` includes up to 128 resolved and unresolved reference entries. Totals remain visible when details are omitted or truncated.

At the public boundary, zero for `inspect_assembly.maxResults`/`maxMembers`, `search_assembly.maxResults`, `find_assembly_extensions.maxResults`, and `get_assembly_context.maxResults` selects that tool's documented default. Zero `maxResponseBytes` likewise selects each assembly tool's existing default budget; a positive explicit value is still honored. The direct `AssemblyToolsContractTests.AssemblyZeroByteDefaultsMatchPublishedBudgetsForLargeResults` compares the first visible content and full outer-page reconstruction for omitted versus zero-byte requests. Its measured first pages exceed 16 KiB for inspect/search and stay within their 24 KiB default, exceed 8 KiB and stay within the 16 KiB extension default, and distinguish Context's 32 KiB standard and 65,536-byte full defaults with content above 16 KiB and 32 KiB respectively. Large decompiled bodies are emitted as line-oriented content: tests reconstruct an 800-line body from `get_symbol_body` and `get_assembly_context` response-window pages, while large `find_symbol` results also continue across pages.

An exclusive `FileShare.None` lock on an otherwise valid managed DLL is exercised through the direct `inspect_assembly` handler. The handler returns typed `TARGET_UNREADABLE`; after releasing the lock, the same query returns the assembly owner result successfully.

For `get_assembly_context`, `detailLevel` accepts compact, standard, or full case-insensitively. It selects default response budgets of 32 KiB, 32 KiB, or 65,536 bytes respectively; an explicit valid `maxResponseBytes` overrides that default. Requested context sections are composed as line-oriented Markdown, and body or graph truncation contributes to the overall completeness status. The `includeCallers` section reports actual reference locations from the selected decompiled root, including type references, rather than treating the members declared by a type as its callers. With `includeReferences=true`, Callers and Impact scan the bounded resolved owner closure and display canonical owner target paths; B.Run and C.LocalRun handles were followed to their owning bodies. The depth-2 Root → B → C fixture returns complete Caller and Impact sections with A.Run visible. A section error fails the context call instead of being embedded in a success response.

Assembly `get_file_tree` and `get_file_skeleton` scan the selected generation's materialized decompiled source root, not neighboring files beside the DLL. File-tree paths can be passed to skeleton directly; skeleton member handoffs can be followed with `get_symbol_body` using the same DLL target. The public stdio regression checks that a neighboring sentinel source file is excluded.

`AssemblySearchScanner.SearchAsync` supports `text`, `external_calls`, and `data_access`. Text searches require a query. The other two kinds use built-in patterns when the query is omitted; a supplied query replaces that pattern. The public `isRegex` option accepts explicit true/false or automatic mode: automatic mode first uses the shared likely-regex detector, then promotes an unmatched pattern with regex metacharacters when it is valid regex or converts invalid `*`/`?` patterns to a glob regex. Regex evaluation has a 250 ms per-match timeout. `DeclarationOnly` restricts matches to declaration headers, including fields, event fields, and enum members, and excludes comments, strings, and method-body uses. `kind=method|type|property` also enables declaration-only matching and selects that declaration kind. Header matches return the declared identifier as `Symbol` even when multiple names share a line.

`FileFilter` accepts a glob or regex, including a leading `!` negation, and matches a normalized path relative to the assembly directory or the file name. Matching files are sorted deterministically; `maxFiles` limits the first files that contain matches, so a nonmatching earlier file does not hide a later hit. The public `maxFiles` default is zero (no additional file-scope limit), and the accepted range is zero through 2,000. The MCP `search_assembly` wrapper defaults `maxResults` to 50 and normalizes an explicit zero to 50; the Core scanner defaults to 100. Both cap at 1,000. `ContextLines` is clamped to 0–5. `search_assembly` supports a bound `v1.<offset>.<binding>` domain cursor in addition to the host's fixed-width decimal response-window token. The domain binding includes the canonical target, root content hash, resolved reference-snapshot hash, and every query, filter, and result-scope argument. Complete any outer byte/token pages before following the domain cursor. Replays return the same next result page; changed arguments, target, root contents, or resolved references return `INVALID_ARGUMENT`. Pages finish after the selected `maxFiles` scope, while the final response stays domain-truncated if more matched files were hidden by that cap. `kind=type` and `kind=method` results carry a navigable handoff and the owning DLL path; type and method handoffs were followed through `get_symbol_body`, with types also verified through `get_class_structure`. Dotted fully qualified type queries in non-regex mode compare the semantic type name after searching its leaf name. Public stdio tests cover cursor and handoff behavior; direct handler tests now add exact nested inspect/search domain and outer-page reconstruction, replay/binding checks, and per-route measured response projections. Full outer-page reconstruction is claimed only for the named direct tests.

`FindAssemblyExtensionsScanner.FindAsync` finds extension methods declared in the target assembly. It can also search the compilation's direct reference assemblies with `IncludeReferences`; receiver type, method name, and namespace filters use case-insensitive matching. Results default to 100 and are capped at 1,000. Missing references remain diagnostics and do not prevent handoffs to declarations in the target assembly; native or invalid images return `INVALID_ASSEMBLY`.

`ResolveTypeOriginScanner.ResolveAsync` resolves a type in the target assembly and, by default, its resolved references. Fully qualified names take the direct metadata lookup path; C# dotted names also support nested types, including generic nested types. Simple names are searched across types and can return an ambiguity result. Reference paths are taken from the compilation metadata reference whose complete Roslyn assembly identity matches the resolved type; if a unique path cannot be proven, the result is marked ambiguous. The payload distinguishes local, reference, and framework origins. When a resolved file path is under the NuGet global packages directory, it also reports the package ID and version. Missing types return `SYMBOL_NOT_FOUND`; native or invalid targets return the shared assembly error result.

The tests cover successful decompilation-based navigation, text and built-in search categories, declaration-only fields, event fields and enum members, extension method filtering, local/reference/framework type origins, versioned assembly paths, nested generic type names, ambiguity, missing and native targets, invalid regexes, and result bounds in [assembly navigation FastTests](../../tests/AiNetCodeNavigator.FastTests/Assemblies/AssemblyNavigationScannerTests.cs).
