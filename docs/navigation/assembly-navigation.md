# Assembly Navigation Core Scanners

The assembly scanners open a managed `.dll` or `.exe` through a resident, read-only decompilation session and use its in-memory Roslyn compilation. ILSpy opens the root PE and resolved dependencies with `PEStreamOptions.PrefetchEntireImage`, so their streams close after each image is loaded and resident sessions do not prevent a normal replacement or deletion. Sessions are reused by canonical target path and keep at most 32 resident targets; idle sessions expire after ten minutes and release their Roslyn snapshots. If all 32 sessions have active operations, acquisition of a new target fails with `ASSEMBLY_SESSION_LIMIT` and can be retried when an operation completes. Each operation holds a generation lease while it reads symbols. Before reuse, the session refreshes the target fingerprint and resolves and fingerprints the current reference set, so changed target or dependency files create a new effective generation and diagnostics. The decompilation cache is bound to that same reference-content snapshot for both reads and publishes; changed references cannot pair stale decompiled source with new Roslyn metadata. A failed refresh never serves the previous generation. If the exact target and reference snapshot of a retained generation are restored, that generation becomes eligible for reuse again with its original status and diagnostics. Scanners do not execute the target binary or modify the target file.

Assembly `inspect_assembly`, `find_symbol`, and the public `get_namespace_tree` type entries bind handoffs to the canonical owner path, owner PE SHA-256, resolved reference-snapshot fingerprint, current owner generation, and canonical documentation-comment ID. The reference fingerprint covers the resolved transitive assembly closure. Assembly `find_symbol` prints the owner `targetPath` beside each reference result so clients can pass the right binary to a follow-up. `AssemblySymbolHandoffResolver` restores opaque handles, verifies assembly origin, refreshes the owner target, validates its current root/reference generation identity, and resolves the declaration only in that target assembly. `get_symbol_body` and the advertised `get_class_structure` follow-up both check the supplied `targetPath` against the handle's owner. Unknown, source, foreign-target, stale, unreadable, and missing-symbol failures are typed MCP errors when every requested body fails; a mixed batch retains successful bodies and reports its failed identifiers as a truncated result. For assembly namespace entries, `get_symbol_body` and `get_class_structure` are tested follow-ups and return data from the owning binary. The assembly namespace tree is also a tested assembly handoff producer. Root-decompiled entries from `get_type_hierarchy` and `find_implementations` now use the same canonical assembly owner, PE hash, reference snapshot, generation, and declaration ID; the public tests follow subtype and implementation handles to the owning body and reject foreign target paths. `get_assembly_context` composes requested body, class structure, actual reference locations, and impact sections; method handles from the reference and impact sections were followed to the owning assembly body. Unresolvable foreign metadata symbols receive no handoff. Assembly `get_call_tree`, `find_references`, and `dependency_graph`, plus relationship results in referenced-assembly source, remain unverified.

The public `inspect_assembly` `continuationToken` accepts the scanner's `v1.<offset>.<binding>` domain cursor as well as the host's fixed-width decimal response-page token. Domain bindings include the canonical target, root hash, resolved reference-snapshot hash, and all query limits/filters. Complete any outer response-window pages before following the domain cursor. Domain-cursor replays return the same next page, and changed query arguments, targets, root contents, or resolved references fail as invalid arguments. Core tests cover Root → B → C, reference replacement, missing references, stale handoffs, and exact-snapshot target restoration. Public stdio tests verify that A references B while B references C, `find_symbol(includeReferences=true)` emits C's owner path and handoff, the same handle roundtrips to C's body, and using A as the follow-up target returns `TARGET_MISMATCH`. They replace C at the same path while the host is active, require the old handle to fail with `STALE_SNAPSHOT`, require a new search/body to expose the replacement, then delete C without stopping the host. A fresh Root search reports no C match with `unresolvedReferences` and truncated completeness, and using the old C handoff through the live Root target fails without returning stale text.

The public `get_type_hierarchy` and `find_implementations` routes resolve assembly handles against the selected owner generation. The tested root-source cases include a derived type, interface implementation, interface method/property implementation, and virtual method/property overrides; each concrete subtype or implementation handoff was followed to the same assembly body. Metadata-only types do not receive source handoffs. Referenced-assembly source scanning remains open.

`AssemblyContextScanner.GetAsync` returns the assembly identity, analysis status, decompilation origin, namespace and type totals, reference totals, and diagnostics. `MaxResults` defaults to 100 and is capped at 1,000 for the namespace and type name lists. Reference details are omitted by default; `IncludeReferences` includes up to 128 resolved and unresolved reference entries. Totals remain visible when details are omitted or truncated.

For `get_assembly_context`, `detailLevel` accepts compact, standard, or full case-insensitively. It selects default response budgets of 32 KiB, 32 KiB, or 65,536 bytes respectively; an explicit valid `maxResponseBytes` overrides that default. Requested context sections are composed as line-oriented Markdown, and body or graph truncation contributes to the overall completeness status. The `includeCallers` section reports actual reference locations from the selected decompiled root, including type references, rather than treating the members declared by a type as its callers. Proven root-source caller handles were followed to the same assembly body. Reference assemblies are listed in the overview when requested, but scanning callers or impact through their source is not implemented yet; only root-decompiled source is searched. A section error fails the context call instead of being embedded in a success response.

Assembly `get_file_tree` and `get_file_skeleton` scan the selected generation's materialized decompiled source root, not neighboring files beside the DLL. File-tree paths can be passed to skeleton directly; skeleton member handoffs can be followed with `get_symbol_body` using the same DLL target. The public stdio regression checks that a neighboring sentinel source file is excluded.

`AssemblySearchScanner.SearchAsync` supports `text`, `external_calls`, and `data_access`. Text searches require a query. The other two kinds use built-in patterns when the query is omitted; a supplied query replaces that pattern. The public `isRegex` option accepts explicit true/false or automatic mode: automatic mode first uses the shared likely-regex detector, then promotes an unmatched pattern with regex metacharacters when it is valid regex or converts invalid `*`/`?` patterns to a glob regex. Regex evaluation has a 250 ms per-match timeout. `DeclarationOnly` restricts matches to declaration headers, including fields, event fields, and enum members, and excludes comments, strings, and method-body uses. `kind=method|type|property` also enables declaration-only matching and selects that declaration kind. Header matches return the declared identifier as `Symbol` even when multiple names share a line.

`FileFilter` accepts a glob or regex, including a leading `!` negation, and matches a normalized path relative to the assembly directory or the file name. Matching files are sorted deterministically; `maxFiles` limits the first files that contain matches, so a nonmatching earlier file does not hide a later hit. The public `maxFiles` default is zero (no additional file-scope limit), and the accepted range is zero through 2,000. The MCP `search_assembly` wrapper defaults `maxResults` to 50 and normalizes an explicit zero to 50; the Core scanner defaults to 100. Both cap at 1,000. `ContextLines` is clamped to 0–5. `search_assembly` supports a bound `v1.<offset>.<binding>` domain cursor in addition to the host's fixed-width decimal response-window token. The domain binding includes the canonical target, root content hash, resolved reference-snapshot hash, and every query, filter, and result-scope argument. Complete any outer byte/token pages before following the domain cursor. Replays return the same next result page; changed arguments, target, root contents, or resolved references return `INVALID_ARGUMENT`. Pages finish after the selected `maxFiles` scope, while the final response stays domain-truncated if more matched files were hidden by that cap. `kind=type` and `kind=method` results carry a navigable handoff and the owning DLL path; type and method handoffs were followed through `get_symbol_body`, with types also verified through `get_class_structure`. Dotted fully qualified type queries in non-regex mode compare the semantic type name after searching its leaf name. These cursor and handoff behaviors have public stdio coverage; the broader per-tool cursor/budget matrix remains open.

`FindAssemblyExtensionsScanner.FindAsync` finds extension methods declared in the target assembly. It can also search the compilation's direct reference assemblies with `IncludeReferences`; receiver type, method name, and namespace filters use case-insensitive matching. Results default to 100 and are capped at 1,000. Missing references remain diagnostics and do not prevent handoffs to declarations in the target assembly; native or invalid images return `INVALID_ASSEMBLY`.

`ResolveTypeOriginScanner.ResolveAsync` resolves a type in the target assembly and, by default, its resolved references. Fully qualified names take the direct metadata lookup path; C# dotted names also support nested types, including generic nested types. Simple names are searched across types and can return an ambiguity result. Reference paths are taken from the compilation metadata reference whose complete Roslyn assembly identity matches the resolved type; if a unique path cannot be proven, the result is marked ambiguous. The payload distinguishes local, reference, and framework origins. When a resolved file path is under the NuGet global packages directory, it also reports the package ID and version. Missing types return `SYMBOL_NOT_FOUND`; native or invalid targets return the shared assembly error result.

The tests cover successful decompilation-based navigation, text and built-in search categories, declaration-only fields, event fields and enum members, extension method filtering, local/reference/framework type origins, versioned assembly paths, nested generic type names, ambiguity, missing and native targets, invalid regexes, and result bounds in [assembly navigation FastTests](../../tests/AiNetCodeNavigator.FastTests/Assemblies/AssemblyNavigationScannerTests.cs).
