# Call Tree Core Engine

The Core call tree engine builds a bounded graph around a Roslyn symbol. Incoming traversal groups source references by caller. Outgoing traversal resolves invocations, explicit and target-typed object creation, and non-invoked member access from block-bodied and expression-bodied declarations. A type seed returns the type and up to five method hints without expanding a graph.

`RequestedDepth` is clamped to 1–5. `TopN` is clamped to at least one edge per expanded symbol; in `Both` mode the incoming groups are considered first, then outgoing groups use the remaining budget. The builder stops at 250 distinct nodes. `Truncated` is true when known edges were omitted or queued nodes remain unexpanded. `HiddenEdgeCount` counts only discovered groups omitted by `TopN` or the hard node cap; `PendingNodeCount` counts queued nodes whose outgoing or incoming relationships were not scanned. Reaching exactly 250 fully expanded terminal nodes does not by itself mark the graph truncated. Symbols are deduplicated with Roslyn symbol equality, call sites for the same edge are combined, and node IDs are local `n1`, `n2`, ... labels.

Outgoing source targets are always retained, including targets in `System` or other framework-named namespaces. Metadata targets are retained by default unless they resolve to BCL assemblies or namespaces. Set `IncludeBcl` to include those framework targets too.

Source-backed nodes carry opaque `h:` handoff IDs when a canonical source identity can be produced. Assembly handoff lines also print the canonical `targetPath` of the node owner. ASCII output lists graph edges, handoffs, known omitted edges, and pending expansions; Mermaid output uses the same nodes and edges, places handoffs and owner paths in comments, and annotates pending expansions. Mermaid labels replace quotes and line breaks so symbol names and paths do not break the flowchart syntax.

The Core entry point throws `ArgumentNullException` for a missing request, solution, or seed symbol. Both renderers throw `ArgumentNullException` for a missing payload. Cancellation is honored during traversal. The public `get_call_tree` handler defaults to incoming traversal, depth 2, `topN` 10, ASCII output, excludes BCL metadata targets, and sets `includeDiagnostics=false`. Assembly calls can opt in to decompilation/navigation and graph-expansion diagnostics; the diagnostic count remains visible when samples are omitted, and source calls do not add diagnostic sections. It accepts `scopeType` (`all`, `production`, or `tests`) and `includeGenerated` (false by default); these filters apply to source nodes before graph limits and source handoffs retain the original solution identity. Assembly targets resolve owner-bound handles and format graph nodes only when their declarations belong to a proven owner source. With `includeReferences=true`, the handler scans each compatible source assembly in the resolved reference closure, merges owner-scoped graphs, applies `topN` fanout globally after merging, then caps visible nodes and edges at 250. Duplicate edges merge only when source node, destination node, and dispatch kind match. Opaque handoffs are created only for final visible nodes. Graph nodes found through metadata are mapped by full original PE identity to a unique source owner; unproven metadata nodes receive no handoff. Incoming C.Read → B.Run → A.Run and outgoing A.Run → B.Run → C.Read were followed to canonical owner bodies at depth 2; incoming C.Read callers in B/C and outgoing B.Run → C.Read were also followed in ASCII and Mermaid, including a Mermaid handoff-to-body roundtrip. The fixture's depth-3 traversal completes, while closure, depth, owner, and output bounds remain honestly incomplete when they prevent the requested traversal and report the relevant next action. Source direct-handler tests reconstruct ASCII and Mermaid independently under byte and token caps, including executable minimum-token recovery, then follow visible handoffs to `get_symbol_body`. Public tests exercise global topN, node, and edge caps. Remaining assembly byte/token/continuation cases are tracked in [MCP navigation registration status](mcp-registration-status.md).
