# Namespace Tree Core Scanner

`NamespaceTreeScanner.ScanSolutionAsync` builds a hierarchical view of declared source namespaces for C# projects in a solution or one named project. Non-C# projects are skipped in a solution scan; naming a non-C# project returns a recoverable error. Project selection accepts an exact name, an unambiguous partial name, or a project path. A duplicate name or a namespace prefix present with source types in multiple projects returns `AMBIGUOUS_SYMBOL` and lists project paths so the caller can select one owner. The payload and formatted title use the selected project's actual name.

The scanner reads Roslyn project documents and does not change source files. By default it excludes generated documents using the same classifier as symbol navigation, where `IncludeGenerated` also defaults to false. Set `NamespaceTreeScanOptions.IncludeGenerated` to `true` to include generated source trees, matching the symbol navigation opt-in. The payload exposes this option, and formatted output labels whether generated source was included or excluded. Therefore, generated-only namespaces are omitted by default and included when the option is enabled. File-scoped and block-scoped declarations share the same namespace tree. Roslyn combines partial type declarations in a project, so each partial type contributes one type to its namespace. Matching namespace names from different projects share a tree node, while their source type counts are added.

Namespace nodes are ordered by ordinal name. Parent namespace segments remain in the result when they contain descendant types, even when they declare no direct types. The total namespace count includes these parent nodes. A namespace with no selected source types anywhere below it is omitted. Types declared directly in the global namespace are not represented as namespace nodes.

`NamespaceTreeScanOptions` bounds each direct Core scan. The default maximum depth is 32 levels; `MaxResults` defaults to 50 and has a 200-entry cap for namespace nodes and a separate 200-entry cap for displayed types. The MCP route requests complete collection of the selected inventory and applies its 1–200 `maxResults` page size after project, namespace-prefix, depth, kind, and generated-source filters. Its combined deterministic page stream contains project-overview rows, namespace rows, and type rows. The same inventory is reachable across `resultCursor` pages, and outer response pages must be reconstructed before using that cursor. `TotalNamespaces` and `TotalTypes` describe the filtered scan scope; analysis depth remains an independent bound. Each `NamespaceNode.TypeCount` counts the types declared directly in that namespace even when `IncludeTypes` is false. An ancestor can therefore have a direct `TypeCount` of zero while `TotalTypes` includes types in its descendant namespaces. Direct Core callers still receive their bounded projection unless they explicitly request complete inventory collection.

The Core scanner does not provide offset or cursor pagination itself. At the MCP boundary, a result cursor pages the completed inventory; traversal depth and filtering remain fixed for that snapshot. Formatted labels and scanner-authored error messages are in English. An unknown project name, a project that cannot produce a compilation, or another scan failure returns an empty payload with an explanatory `Error`. Cancellation is propagated to the caller.

For source MCP calls with no `project` or `namespacePrefix`, the scanner returns a depth-one project overview with per-project namespace/type counts. Duplicate project names include their relative project paths. Supplying a namespace prefix without a project selects the unique C# project that declares source types under that namespace; zero matches is invalid and multiple matching projects are ambiguous. A project or unique namespace selection drills into the namespace tree.

The MCP host registers `browse_target` with `view=namespaces` for source and managed-assembly targets and adds public namespace-prefix, kind, and include-types filters. A no-filter source query returns a depth-one project overview with namespace/type counts and relative paths for duplicate project names. A prefix without a project searches descendant namespaces and selects only a unique project owner; zero matches are invalid and multiple project owners return `AMBIGUOUS_SYMBOL`. Source and assembly type entries carry stable references when representable. Domain pages preserve the complete discovered inventory independently of outer response paging. See [Shared Symbol Resolution](symbol-resolution.md) for reference semantics. See [MCP Host](../mcp-host.md).

Recovery instructions follow the target kind and the selected scope. For source results, an already-selected project is not requested again; use a narrower/deeper namespace prefix or increase depth only within the allowed bound. Assembly recovery names a namespace prefix and does not ask for a source project. The public depth is capped at three, while direct Core scans are capped at 32; at either cap, the next action narrows the prefix instead of recommending an invalid depth. MCP `maxResults` remains the page size for `resultCursor`, not an analysis bound. Reconstruct all outer response pages before following the next domain cursor.

The result cursor is bound to the target snapshot, project, namespace prefix, depth, type-selection filters, generated-source option, and `maxResults` page size. Reusing it with a changed query or page size returns `RESULT_CURSOR_ARGUMENT_MISMATCH`; changed target contents return `STALE_SNAPSHOT`. Response byte and token budgets may change while reading outer response pages. Reconstruct all outer pages for one result before using its next `resultCursor`.

The namespace response includes `view=namespaces` and `totalsScope`. In a project overview, both namespace/type totals cover loaded C# projects. In a hierarchy, `totalTypes` covers matching declarations throughout the selected project (including deeper declarations), while `totalNamespaces` covers the selected project or selected prefix tree within `namespaceDepth`. Prefix filtering does not turn the project type total into a prefix type total. Depth omissions and paging remain separate. Only this view invokes the namespace scanner; it does not enumerate the source scope inventory.

`project`, `namespacePrefix`, `depth`, `includeTypes`, `kind`, and `includeGenerated` are nullable wire options so explicit defaults are still rejected with `view=scope`. Inventory cursors bind the original view and complete options, including argument presence. Read all outer response pages before advancing a cursor; depth recovery retains `view=namespaces` and the selected project/prefix.
