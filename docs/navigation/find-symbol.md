# Find Symbol

`FindSymbolScanner` searches C# source declarations in the C# projects of a Roslyn solution. In mixed-language solutions, declarations and source locations from non-C# projects are excluded from results and suggestions, matching the C# coverage in index scope and namespace tree. It supports case-insensitive substring matching, `*` and `?` wildcards, regular expressions recognized by the shared matcher, Markdown backticks around identifiers, and dot-separated type/member names. Results include symbol kind, signature, source path and line, the owning Roslyn `Project.Name`, and a stable reference when the exact declaration round-trip succeeds. This is the project label; assembly searches identify the owning assembly separately. See [Shared Symbol Resolution](symbol-resolution.md) for reference semantics.

The MCP JSON projection keeps the first visible declaration location in the top-level location fields. It omits `locations` only when that array would contain exactly one item whose path, line bounds, and project name are byte-for-byte identical to those primary fields. Results with multiple visible declaration locations keep the complete array, including the primary location; this preserves partial declarations and per-location filtering. The Core scanner retains the complete location array.

A `namePatterns` batch acquires one source lease and computes symbol identities from one resident snapshot for every pattern. Assembly batches hold one root generation lease; referenced owner results are returned only when their owner content still matches the root's captured reference closure.

The kind filter accepts all symbols or one of class, struct, interface, enum, delegate, record, record class, record struct, method, property, field, and event. Plain class and struct filters exclude record declarations; `record` includes both record classes and record structs. A kind mismatch returns an explanatory message listing the kinds found for the name.

The scope filter accepts `all`, `production`, or `tests`. Classification is applied to each source location using its Roslyn project and document: test project metadata, recognized test project names or paths, and recognized test file paths identify test locations. `all` includes both groups. This keeps same-named declarations in separate production and test projects scoped to their own locations.

For managed assemblies, the same filter classifies each scanned owner from its assembly project name, framework references, and canonical assembly path. It is applied before counting and paging. The decompiler's generated cache path does not affect whether an assembly is treated as production or tests.

Generated source locations are excluded by default. Set `IncludeGenerated` to `true` to include them in any scope. Generated locations are recognized from `obj/` paths, `.g.cs`, `.g.i.cs`, `.generated.cs`, and `.designer.cs` suffixes, `<auto-generated` headers within the first five lines, or a `GeneratedCodeAttribute` on a declaration in the document. Filtering is applied per source location, so a partial type with both generated and handwritten declarations retains only handwritten locations by default and returns both when generated source is included.

Core callers may use `maxResults` as a scanner display bound. The MCP handler applies source scope and kind filters before a deterministic combined result page; `maxResults` is that page size, and a `resultCursor` makes every known entry reachable, including entries from a `namePatterns` batch. Source batches share one resident solution snapshot, and assembly batches share one root generation and reference snapshot. Result-page availability does not mark the analysis partial. Name misses may include similar symbol suggestions. The MCP host registers `find_symbol` for source and managed-assembly targets; see [MCP Host](../mcp-host.md) for its public routing.

For managed assemblies, symbol results include the canonical `targetPath` of the assembly that owns the symbol alongside its stable reference when available. Use that owner path for `get_symbol_body`; passing the searched root assembly for a referenced symbol returns `TARGET_MISMATCH`. When references cannot be resolved, a no-match result identifies `unresolvedReferences` and provides a recovery action, so it does not imply that the full reference closure was searched.

The MCP `includeReferences` option applies to managed-assembly searches: it adds matches from resolved referenced assemblies. Source searches ignore this option. The transport-free source and assembly contract tests reconstruct domain pages exactly, verify batch/query cursor binding, and follow returned references to their owning target. Source outer-response tests also reconstruct byte- and token-limited responses against a broad-budget query.


Discovery filters are applied before result paging: source `project` selects exactly one loaded owner by exact name (ordinal ignore-case) or its canonical path, `namespaceFilter` is an ordinal ignore-case substring of the full declared namespace, and `signatureFilter` is an ordinal case-sensitive substring of the returned signature. Whitespace-only namespace/signature filters mean no filter; meaningful signature characters, including spaces, are matched literally. Duplicate project names require the returned path; empty/unknown selectors fail, and assembly targets reject project selection.

`extensionOnly=true` selects actual Roslyn extension methods, permits enumeration with both pattern inputs omitted, and accepts only omitted/method kind. Otherwise the existing one-pattern-or-one-to-ten-patterns contract remains. `receiverType` requires extension-only and uses declared receiver alias/qualified suffix equality, without assignability or expression-applicability checks. Omitted/whitespace receivers mean no receiver filter. A name substring uses the existing `*name*` pattern. Results identify extension status, namespace, receiver, signature and stable owner reference when proven. Assembly extension discovery retains resolved-owner opt-in and compact/detailed diagnostics; incomplete reference closure is explicit. Cursors bind all effective filters, pattern batching, snapshot and page size.

After reading all outer pages, follow a returned `resultCursor` first. On a final assembly-extension page, `incompleteRelationships` requires restoring missing assembly references and repeating the query; increasing `maxResults` cannot repair missing owners. Display-limit recovery is offered only for an actual `maxResults` omission.
