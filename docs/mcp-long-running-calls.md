# MCP Long-Running Calls and Continuations

`LongRunningToolCallStore` is an internal host-side building block used by navigation registrations. The Generic Host owns it through `NavigatorHostRuntime`. A registration supplies an operation delegate and a stable argument key; the store owns the delegate's cancellation token and gives the caller an opaque `operationToken` when the operation exceeds its response window. The host waits at most 15 seconds on the first call and one second on a poll, with independent internal test overrides. These are operation wait bounds; formatting and transport add their own overhead. It links the store lifetime to `IHostApplicationLifetime.ApplicationStopping`, so active work is cancelled before resident registries are disposed.


Running controls preserve the status preamble and `operationToken=<token>` convention. They include monotonic non-negative `elapsedMilliseconds`, the highest reached `phase` (`loading`, `refreshing`, `identifying`, `analyzing`, `formatting`), `retryAfterMilliseconds: 1000`, and a complete `nextAction`. Clients wait at least that interval before polling the same tool, target and query, preserving an active result cursor and omitting outer continuation tokens. Source dependency progress counts each exact snapshot/project/document need once when satisfied by new, shared or cached successful facts; failed needs do not count. Broad collection and depth-1 outgoing roots publish a fixed known total. Deeper outgoing requests omit totals throughout frontier discovery, including reuse of full resident facts. Other navigation tools publish phases without document counters. Progress is an immutable request-owned snapshot; a scoped host adapter translates typed Core events without retaining MCP progress in cache jobs.

Operation tokens use the continuation store's cryptographically random fixed-width 39-digit generator. The operation store reserves an actual collision-free token before starting work and measures required running controls at maximum Int64 elapsed time across every phase using UTF-8 and `cl100k_base`. The maximum measured byte/token pair, with the public byte floor, is the first-call admission minimum. Insufficient budgets return an atomic `RESPONSE_BUDGET_TOO_SMALL` error with both minima and an unchanged fresh-call action before any job starts. A running poll that cannot fit its required control returns that same fixed pair while retaining the admitted operation/token. Retry with exactly both advertised budgets. Optional document counters may be omitted at tight budgets; the status, token, elapsed time, phase, retry interval and action remain complete. Budgets unable to represent the complete error envelope retain the existing validation behavior.

At the four-active-operation limit, a fresh request receives the budgeted recoverable `TOO_MANY_OPERATIONS` error with required `retryAfterMilliseconds: 1000` and an action to wait at least that interval, then retry the original request without an operation token. The rejected request starts no work, retains no admitted operation and returns no usable token; its temporary preflight token reservation is released. Completing or cancelling admitted work frees capacity. There is no queue or automatic server retry. The delay and action are required error fields, so optional context cannot displace them; a budget unable to represent the complete required error retains atomic validation behavior.

Operation tokens are bound to the tool name, target path, stable argument key, and (for domain-cursor operations) the exact domain cursor. A poll repeats that same identity and may cancel its own wait without cancelling the underlying operation; a valid poll resets the running idle deadline. Domain cursors may accompany an operation token for the same inspect page, while an outer response-page token cannot. A focused store regression verifies that a poll with a changed cursor is rejected and the original cursor poll completes without restarting work. Cancellation of the initial request cancels its work. Store disposal and its linked host-lifetime token cancel and await work owned by that store. Delegates execute on the thread pool so a synchronous callback cannot hold the store lock or delay the response window. The default limits are four active operations and 32 completed operation records. Running and completed records expire after 30 minutes of inactivity by default; running work is cancelled by its idle timer even when no later call arrives. Exceptions from tool delegates become a recoverable `OPERATION_FAILED` result without exposing exception details.

Completed text responses pass through `McpResponseFormatter`. A response that does not fit is returned as a page with `completeness=truncated` and an opaque `continuationToken`. This token is reserved for immutable outer text pages. The status, analysis metadata, token, text units, and formatter markers are measured together against the requested UTF-8 byte and token limits. Outer tokens refer to stored text snapshots and are bound to the original tool, canonical target, arguments, and result section. Response byte/token budgets are per-request output options and may be increased when retrying the same continuation token; successful page projections are cached per token and budget pair. Budget-error responses do not consume a cache variant, so the exact advertised retry remains available. A later page has its own continuation token, so clients never need to interpret an internal UTF-16 offset. Pages preserve complete newline-delimited units and Unicode scalar values.

Continuation snapshots expire after 30 minutes of inactivity by default. Retention is bounded to 32 snapshots, 8 MiB of source text, 512 page tokens, and four cached byte/token budget pairs per token; these limits and the retention duration are injectable for tests and host configuration. Unknown, expired, mismatched, or capacity-rejected continuations produce recoverable errors. A first atomic unit that cannot fit produces the formatter's budget error; callers can retry that same token with the advertised byte/token pair. Structured content is returned only when its complete text fits; a structured response that would require pagination returns `STRUCTURED_RESULT_TOO_LARGE` without attaching structured content to a partial page. Non-text tool results are rejected as invalid store input.

The `inspect_assembly`, `search_assembly`, and `find_symbol` with `extensionOnly=true` registrations expose an opaque `resultCursor` for domain pages. The shared response store maps it to the Core scanner cursor and binds it to the tool, canonical target, stable arguments, real assembly-owner/reference/generation snapshot ID, and named result section. A cursor replay for the same binding keeps the same public token; malformed Core cursors return `INVALID_ARGUMENT`, query/target/page-size mismatches return `RESULT_CURSOR_ARGUMENT_MISMATCH`, expired shared cursors return `RESULT_CURSOR_EXPIRED`, and changed assembly snapshots return `STALE_SNAPSHOT`. If a domain page itself needs byte pagination, finish those outer pages before using its JSON `resultCursor`.

Successful source and assembly result pages expose `snapshotId`, normalized `analyzedScope`, and `analysisCompleteness` in the status preamble. `resultContinuation=available` and concrete `omissions` appear when present; if navigation metadata is emitted and either line is absent, it means no result cursor is available or no analysis omission was reported. The scope is escaped to one line so literal newlines in search patterns cannot create additional headers. `analysisCompleteness` describes analysis limits; an outer response page never changes it. A domain page size with a live `resultCursor` is reported as `resultContinuation=available`, not as an omitted analysis hit. Scanner or traversal limits such as a matching-file cap are reported as `analysisCompleteness=partial` with their specific omission reason. Assembly `snapshotId` comes from the exact owner content, resolved reference snapshot, and generation used by the scanner; source IDs are computed from the loaded solution's project/reference identity and document contents at the source analysis boundary. Snapshot IDs are compact opaque aliases, not complete SHA-256 values; cursor binding retains the full owner/reference/generation identity. The typed Core `NavigationAnalysisMetadata` contract travels with the result; the host does not infer completeness from response text. `operationToken` is reserved for polling, `continuationToken` for immutable outer response pages, and `resultCursor` for domain pages. Budget changes affect only the outer projection and do not change the query. The shared continuation store bounds outer and domain tokens by the same TTL, snapshot, byte, and page limits; it counts stored targets, argument bindings, section IDs, and Core cursor material. The reported metadata itself participates in exact byte/token retry minima.

These classes provide lifecycle and response-continuation mechanics; they do not validate general tool schemas or define other tool-specific argument contracts. Real MCP stdio/registration evidence is recorded separately in the current [navigation registration status](navigation/mcp-registration-status.md). Component tests cover polling-waiter cancellation separately from cancellation of shared work.

Continuation tokens are fixed-width, 39-digit random decimal values, so the visible token prefix has a stable `cl100k_base` cost when the formatter computes an exact retry minimum. Each issued token is inserted once and keeps its original snapshot offset; a budget change creates another token/page projection rather than rebinding an existing token. On cached operation-poll replay, the store verifies that the response's successor or domain cursor is still live. If a domain cursor expired, the operation's immutable Core result can produce a fresh opaque public cursor; the expired cursor remains expired. A continuation-page replay never re-registers expired domain cursors or rewrites its stored snapshot: it returns the cached outer page byte for byte, and attempting the expired `resultCursor` independently returns `RESULT_CURSOR_EXPIRED`. Expired outer successors can be projected again from the same outer snapshot and offset without changing the original token's binding. Completed operation results are retained once per operation and successful response-budget pair. Repeated or concurrent final polls reuse the same first-page result and snapshot identity while its continuation remains live; changed budgets create separately cached projections within the configured per-operation variant bound. Completed-record retention runs when background work actually completes, even if nobody polls afterward. Expiry, execution completion, and disposal share cancellation ownership so expiry cannot cancel a source after another path has disposed it.

Delegate results with `operation=retry` remain retry controls, without an outer success status or continuation snapshot. They are returned unchanged if they fit the caller's byte and token budgets; otherwise the store returns an atomic `RESPONSE_BUDGET_TOO_SMALL` error with `max(512, measured UTF-8 bytes)` and the exact measured token count, never a truncated retry action. A completed operation's stored error uses the same measured recovery pair and replays the original error unchanged when retried with both values. Immutable projections over 65,536 bytes remain unfittable and direct callers to narrow the request. Retry controls are not cached as completed navigation successes. A delegate `operation=running` control is rejected with `OPERATION_CONTROL_UNSUPPORTED` because its operation token belongs to another store and this store cannot extend that token's lifecycle. The store's own pending operations continue to use its bound `operationToken` protocol.
