# MCP Long-Running Calls and Continuations

`LongRunningToolCallStore` is an internal host-side building block for tool registrations. It does not start the MCP host or register public tools. A registration supplies an operation delegate and a stable argument key; the store owns the delegate's cancellation token and gives the caller an opaque `operationToken` when the operation exceeds its response window.

Operation tokens are bound to the tool name, target path, and argument key. A poll repeats that same identity and may cancel its own wait without cancelling the underlying operation; a valid poll resets the running idle deadline. Cancellation of the initial request cancels its work. Store disposal and its linked host-lifetime token cancel and await work owned by that store. Delegates execute on the thread pool so a synchronous callback cannot hold the store lock or delay the response window. The default limits are four active operations and 32 completed operation records. Running and completed records expire after 30 minutes of inactivity by default; running work is cancelled by its idle timer even when no later call arrives. Exceptions from tool delegates become a recoverable `OPERATION_FAILED` result without exposing exception details.

Completed text responses pass through `McpResponseFormatter`. A response that does not fit is returned as a page with `completeness=truncated` and an opaque `continuationToken`. The status, token, text units, and formatter markers are measured together against the requested UTF-8 byte and token limits. Continuation tokens refer to immutable text snapshots and are bound to the original tool, target, and arguments. Response byte/token budgets are per-request output options and may be increased when retrying the same continuation token; results are cached per token and budget pair so replay stays stable. A later page has its own continuation token, so clients never need to interpret an internal UTF-16 offset. Pages preserve complete newline-delimited units and Unicode scalar values.

Continuation snapshots expire after 30 minutes of inactivity by default. Retention is bounded to 32 snapshots, 8 MiB of source text, 512 page tokens, and four cached byte/token budget pairs per token; these limits and the retention duration are injectable for tests and host configuration. Unknown, expired, mismatched, or capacity-rejected continuations produce recoverable errors. A first atomic unit that cannot fit produces the formatter's budget error; callers can retry that same token with the advertised byte/token pair. Structured content is returned only when its complete text fits; a structured response that would require pagination returns `STRUCTURED_RESULT_TOO_LARGE` without attaching structured content to a partial page. Non-text tool results are rejected as invalid store input.

These classes only provide lifecycle and response-continuation mechanics. They do not validate general tool schemas, define tool-specific argument contracts, or claim MCP stdio/registration behavior. Those remain separate acceptance work.

Continuation tokens are fixed-width, 39-digit random decimal values, so the visible token prefix has a stable `cl100k_base` cost when the formatter computes an exact retry minimum. Each issued token is inserted once and keeps its original snapshot offset; a budget change creates another token/page projection rather than rebinding an existing token. Completed operation results are retained once per operation and response-budget pair. Repeated or concurrent final polls reuse the same first-page result and snapshot identity; changed budgets create separately cached projections within the configured per-operation variant bound. Completed-record retention runs when background work actually completes, even if nobody polls afterward. Expiry, execution completion, and disposal share cancellation ownership so expiry cannot cancel a source after another path has disposed it.
